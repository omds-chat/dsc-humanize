## 4.1 资产包格式与加载期包文档

已知约束:

- 包的目录布局、元数据字段与五类内容字段由 dsc-humanize-asset-template 的规范 1.1.0 定义,本仓库不另立格式;内核只约定读取时消费的字段与加载期包文档的形状,见 3.5。
- 资产包必须在元数据里声明包含哪几类内容;缺声明、声明与内容不一致都按格式错误整包拒绝,见 2.8。
- 一个包可以只包含五类中的任意几类,允许的类型集合固定,纯人设包与纯对比示例包都合法。
- 引入包不整体替换用户当前配置:每一类内容的来源由用户分别选择,来源是某个包或用户自写。
- 导入即校验:标签标识唯一;包内声明标签集时规则引用的标签必须存在;每条规则至少给出一个策略字段;数值在声明范围内;人物设定的标识、名称、前缀齐全。
- 格式版本是必填的三段数字,当前 1.1.0;格式规范要求加载方拒绝主版本不同的包,内核读取已比较主版本,主版本不同以 format-version-unsupported 拒绝。
- 1.1.0 的新特性(examples 类型、exclude_keywords、patterns、dimension)按包声明的 formatVersion 开门:按 1.0.0 判定的包声明任一新特性即整包拒绝,错误码 format-version-feature 与模板校验器对齐;判定所用版本缺省取包声明值(自动识别)。
- 资产包必须能承载界面里的每一个属性,且导出后能原样导入。
- 包本身只读、组合不回写、组合结果落在当前使用快照,见 2.9.2 与 2.9.3;格式定稿不得引入需要改写包字段的机制。
- 同类内容跨包时的取舍已定,见 2.9.1:不设跨包优先级,由用户选择其一或两者并用;冲突由用户自行处理。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 加载期包文档是否固定为「元数据加按类型内容」 | 它是目录包的一次读取投影;是否随导入通道(文件、文本、地址)变化,取决于 4.2 的导入方式 |
| 内核支持的格式主版本范围 | 格式规范要求加载方拒绝主版本不同的包;内核读取已比较主版本(只收主版本 1),更高主版本的接受范围随内核版本策略与升级路径定 |
| 导入导出路径与打包分发形态 | 取决于合集与索引如何收资产,以及用户导入的是文件、文本还是地址 |
| 文本编码、换行与大小上限 | 取决于导入通道与存储方式 |
| 编辑器字段定义与资产字段的同源方式 | 取决于界面实现方式,决定由哪一侧生成校验规则 |
| 用户自写内容存在哪里、是否也要声明类型 | 取决于 4.2 的存储取舍与打包分发形态;若自写内容与包走同一套校验,它就是独立文件,否则只能作为装配状态的一部分 |

「同一类型出现多个来源时如何合并与解决冲突」一项已由 2.9 定稿,不再作为本节待定项:取舍由用户完成,内核不设优先级。仍待定的只剩冲突如何呈现,它依赖 4.2 的界面能力。

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 直接把内核的类型定义当对外格式 | 类型是实现的内部形状,改实现就破坏用户资产;格式需要独立版本与稳定边界 |
| 复用插件清单或插件包格式承载资产 | 插件是可执行产物,资产是数据;混用会把执行、权限与安装生命周期带进资产,「一比一导入导出」会被插件版本牵制 |
| 允许资产携带可执行脚本或模板表达式 | 资产必须能被界面完整编辑并静态校验;可执行内容无法保证一比一往返,也把内容问题变成代码审计问题 |
| 无 Schema 的自由 JSON,字段全部可选 | 给不出字段级错误,也无法保证「不存在用户无法设置的属性」 |
| 多套格式并存、导入时静默迁移 | 迁移必然改写用户资产,与一比一冲突;版本不兼容应显式报错,由用户决定是否转换 |
| 整体替换式导入:导入一个包即顶掉用户当前所有类型的来源 | 用户的配置是多来源合成的,整包替换会静默清掉用户自写与其他包的内容,用户只能感到「设置有东西丢了」;也与 1.3 的「预设只是来源」和 2.5 的一比一冲突 |
| 包不带类型声明,由加载方按内容猜测类型 | 五类里存在判断不唯一的情形(人设前缀与提示词模板都是文本),猜测结论随启发式改动而变化,同一份包在不同版本下归类不同,猜错还静默生效;声明是校验与来源选择的前提 |
| 用「缺省即包含五类」的隐式声明 | 会凭空造出空的标签集与空策略表,而「选了空集合」与「没有这一类」在装配时是两种含义,混在一起就无法区分用户是清空了还是没选 |
| 组合时回写资产包,或把当前使用快照存进包内 | 包一旦随使用变化,同一个包就不再指同一份内容,哈希、合集校验与用户之间的交换都失去基准;也违反 2.9.2 的只读前提 |
| 给包排顺序或用「后导入覆盖先导入」消解同类冲突 | 顺序是内核替用户做的内容取舍,用户看不到也改不动,与 1.2 的「不承诺固定形象」冲突;见 2.9.1 |

## 4.2 编辑界面

已知约束:

- 宿主已提供 `ui:slot` 槽位能力,本插件已用其中四处承载市场标签、设置页、工具条开关与状态通知(见 [asset-market.md](asset-market.md) 6.4);槽位形态是「插件交描述、宿主渲染」的声明式落点,资产编辑界面需要的逐项编辑、校验提示与预览能否承载,仍取决于槽位的控件能力。界面落在哪里,受宿主槽位形态约束。
- 插件存储有单插件容量上限,且清除站点数据即丢失,不能作为资产的唯一副本。
- 一比一导出要求界面字段与资产字段同源,不能各写一套。
- 界面必须覆盖资产包的每一个属性,包括长文本、数值、枚举与列表。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 界面落点 | 宿主已开放 `ui:slot` 槽位,但编辑视图承载在哪类槽位、宿主是否允许承载编辑视图仍未定 |
| 字段分组与校验提示 | 取决于资产格式的字段全集 |
| 预览方式 | 是否展示拼接后的提示词、是否展示命中标签,取决于宿主是否提供请求上下文 |
| 来源与冲突的呈现 | 同类内容来自两个包并一起使用时,界面上如何标出冲突、由用户在何处处理,取决于格式(4.1)与界面能力;取舍由谁做已定,见 2.9.1 |
| 导入导出交互 | 取决于资产打包形态,以及宿主是否允许文件读写 |
| 资产存放位置 | 文件、插件存储还是浏览器本地数据库,取决于容量与生命周期要求;当前使用快照(2.9.3)不得落在资产包内,其介质已定为 IndexedDB(4.6) |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 只提供预设选择器,不提供逐项编辑 | 与「不存在用户无法设置的属性」直接冲突,预设只能是起点 |
| 用一个 JSON 文本框作为唯一编辑界面 | 技术上能设置每一项,但没有字段级校验与说明,普通用户无法使用,与「由用户在插件界面输入与编辑」不符 |
| 界面自建一套字段模型,导出时再映射 | 两套模型必然漂移,漂移的部分就是用户设置不进去或导出丢失的属性 |
| 把资产存进插件存储当作唯一副本 | 容量不足,且随站点数据清除而丢失;资产应以文件形式由用户持有 |
| 由插件改写宿主页面结构来造界面 | 越过插件契约,宿主改版即失效,也会干扰其他插件 |

## 4.4 资产生态信任体系

已知约束:

- 资产是纯数据,由用户导入;导入后的效果完全取决于内容,不取决于它来自哪里。
- 资产有两个来源:内置合集与社区合集。两者都只是索引与分发,不是内核的一部分,内核不认识来源。
- 组织在插件体系里已有证书链与来源校验;资产生态不沿用这套链,两者是独立信任域(2.10)。
- 身份与锚点已定,见 2.10:本插件在插件生态里是一个插件,在资产生态里是自签根 CA;资产来源的验签以本仓库 `certs/dsc-humanize/dsc-humanize-root-ca.crt` 为唯一锚,该根与 ds-chat 根证书无关。本节只处理签名覆盖范围、签名者与结论呈现这些仍待定的部分。
- 资产包只读(2.9.2):包在磁盘上不可变、组合不回写,因此一份包的校验结论与它交付给用户的内容始终对应。
- 资产会被用户之间交换,同一份包在不同用户处的行为应当一致。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 资产是否签名、签名覆盖哪些字段 | 取决于资产打包形态与是否允许部分更新 |
| 签名者是谁:作者还是合集 | 取决于合集在生态里的角色,是只做索引还是同时托管与背书 |
| 信任结论如何呈现 | 需要先定义结论的几种状态,以及界面能承载的信息量 |
| 失败时是否阻断 | 组织在插件体系里的现行口径是校验失败只警告、不阻断;资产是否沿用需要明确 |
| 资产更新与撤回 | 已导入的资产如何得知上游变化,是否需要撤回机制 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 以人工逐包审核作为唯一准入 | 无法扩展,审核结论也不可机器验证,用户仍无法判断手里的包是否被改过 |
| 把资产当可执行产物做代码签名与执行沙箱 | 资产是数据,没有执行语义;引入沙箱只增加复杂度,不增加实际保障 |
| 由中心化白名单垄断分发 | 与「预设只是来源之一」冲突;用户应能导入自建或第三方资产 |
| 运行时从任意地址自动拉取并信任资产 | 未经用户确认的远端内容会直接改变助手行为;地址可达不等于内容可信 |
| 以「未签名」本身作为拒绝加载的理由 | 与组织现行的「只警告、不阻断」口径相反,也会把信任问题变成可用性问题 |

## 4.5 远端资产能力

> 状态注记:宿主的受控资产读取能力(`assets:read`)已按 [asset-market.md](asset-market.md) 7.3 的首选候选落地,远端资产可经该通道读取;本节保留,记录当时的候选与排除理由,并作为「宿主回退到没有该能力的旧版,或通道被移除」情形的后果口径。

已知约束:

- 插件不是内置插件。宿主能力表里的 `net:fetch` 只对内置插件开放:第三方插件的清单声明它时按未知能力拒绝,调用层再校验一次。在 `assets:read` 落地前,3.5 的地址路径没有通道可用,远端资产通道当时不可用;现状见上方状态注记。
- 内核不发网络请求(3.6):地址资产由调用方注入通道取回,内核只做 JSON 解析与校验。通道存不存在不改变内核的形状。
- 若做,候选形状是宿主新增一条受控的资产读取能力,不是开放通用网络:只允许 https,不带凭证(不附带 Cookie、Authorization 与自定义请求头),限体积与超时,首次访问某个地址时需用户确认。
- 跨域是否放行由对方服务器决定:浏览器发出的请求能否读到响应体,取决于对方的响应头;静态站点通常没有配置,插件侧无法绕过,也不能靠改地址或换协议绕过。
- 探测结论只能三态:取到内容;读到明确的错误状态码,说明对方已放行、只是该地址的内容不对;无法判定。第三态无法区分「地址无效」与「对方未开启跨域」,提示文案固定为「该链接无效或对方未开启跨域访问」。
- 新增一条对插件可见的能力,要同时进能力联合、可见集合、服务注册、引擎策略表与两处规范副本;限流窗口与超时由引擎侧统一,口径与既有能力同源。

候选:

| 候选 | 形状 | 代价 |
|:---:|:---:|:---:|
| 宿主新增受控资产读取能力 | 只允许 https、不带凭证、限体积与超时、首次地址需用户确认的单动作能力 | 属于新增能力,要与能力表、限流契约一起定;跨域仍由对方服务器决定,三态里最坏的一态只能给出合并文案 |
| 维持本地导入 | 资产包由用户下载到本地后导入,远端地址只作为获取入口的提示 | 没有一键使用远端资产的能力;合集与索引只能引导用户自行下载,地址失效时也没有插件侧的探测 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 在清单里申请内置插件的那条取字节能力,或复用内置插件的通道 | 该能力只对内置插件开放,申请会被拒;绕过等于越过能力契约,「能力由宿主授予」这条前提也随之失效 |
| 插件自行请求任意地址 | 把网络暴露面从「一个受控动作」扩大到「任意源」,而资产是纯数据,不需要这种表达力 |
| 用公共跨域代理中转请求 | 代理能看到资产内容,信任面从对方服务器挪到第三方;代理的可用性也不由我们控制 |
| 把「无法判定」一律报成地址无效,或一律报成对方未开跨域 | 两种原因在浏览器侧无法区分,单报一种会把用户引到错误的排查方向;文案必须同时覆盖两种可能 |
| 探测成功就把该地址记为可信来源 | 地址可达不等于内容可信,信任结论属 4.4;探测只回答「这次能不能读到字节」 |

为什么现在不做:

- 这条能力的形状要与引擎侧的「唯一 core 调用通道」与限流契约一起定:资产读取只是新增能力的一个用例,先按资产的需要定一条网络形状,等通道与限流口径落定后就要返工。
- 三态探测的失败分支直接决定 4.2 的界面文案与导入流程,而界面落点尚未定;先定能力会把文案与流程锁在未定的界面上。
- 跨域不受我们控制:先做也只能覆盖一部分托管方式,结论随托管方式而变,不适合当成统一定稿。
