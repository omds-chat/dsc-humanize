## 一、产品定位

### 1.1 目标

dsc-humanize 要让 ds-chat 里的助手更接近用户期望的样子。衡量标准只有两条:

- 表达能力:用户想表达的人设、语气、应答偏好与边界,都能写进资产;
- 还原能力:写进资产的内容在每次规划里按预期生效,不被插件自身的默认值改写。

两条都不以「像某种人」为标准。插件不评价用户的选择,只保证选择能被完整表达并稳定执行。

### 1.2 不承诺固定形象

插件不定义「好助手」的标准形象,也不内置任何性格。理由:

- 用户期望彼此冲突:有人要简洁,有人要健谈,有人要克制。任何默认形象都会对一部分用户变成偏差,而且偏差是静默发生的,用户只能感到「不对劲」,说不出哪里被改了。
- 一旦插件对形象有承诺,资产编辑就退化成「在几种预设里选一种」,与 1.1 的表达能力直接矛盾。
- 插件唯一稳定的承诺是「你设置什么,就按什么执行」。这个承诺不依赖任何具体风格,也不会随版本改变。

「人性化」是这类资产的名字,不是强制的风格。资产里写什么,助手就呈现什么。

### 1.3 由定位推出的三条硬约束

| 约束 | 含义 | 排除的做法 |
|:---:|:---:|:---:|
| 界面可设置项覆盖资产全部属性 | 资产包的每个属性都有对应的编辑入口 | 只提供预设切换、细节靠改文件 |
| 导入导出一比一 | 导出再导入语义不变,不静默补默认值、不丢字段 | 界面私有字段、导出时再做映射 |
| 预设只是来源 | 内置合集提供的是可导入的资产包 | 把内置合集当成插件支持的全部形态 |

三条是定位的直接推论,不是实现细节。任何一条被推翻,1.2 的「不承诺固定形象」就不再成立。

## 二、内核与资产的边界

### 2.1 三方职责

| 角色 | 负责 | 不负责 |
|:---:|:---:|:---:|
| 内核 | 文本到标签、标签到策略、策略与提示词到注入片段 | 不定义助手长什么样;不执行请求;不读写宿主状态 |
| 资产 | 分类标签、策略库、提示词模板、人物设定 | 不含可执行逻辑;不决定如何分类与合并 |
| 宿主 | 决定策略是否落到请求参数与系统提示词上 | 不替用户决定内容 |

按这个分工,分类管线、策略执行与注入拼接属于内核;策略库、提示词模板、人物设定与分类标签属于资产。三者之间只传递数据:资产是输入,内核是计算,宿主是落点。内核不直接触达宿主,资产不直接触达请求。

### 2.2 归类判据

| 判据 | 归内核 | 归资产 |
|:---:|:---:|:---:|
| 是否含可执行逻辑 | 含 | 不含,只含数据 |
| 随什么版本演进 | 插件版本 | 资产包版本 |
| 用户能否替换 | 不能 | 能,且必须能 |
| 回答的问题 | 怎么算 | 算成什么 |

一句话:内核决定怎么算,资产决定算成什么。判断一段内容是内核还是资产时,先看它回答的是哪个问题,而不是看它写在哪个文件里。

### 2.3 资产的四类内容

| 类别 | 内容 | 在内核中的作用点 |
|:---:|:---:|:---:|
| 分类标签 | 标签标识、语义说明、关键词、权重 | 限定分类器可输出的标签范围 |
| 策略库 | 兜底策略、标签到请求参数的规则、合并优先级与生效阈值 | 决定命中标签后各请求参数如何收敛 |
| 提示词模板 | 注入到系统提示词的文本片段 | 决定注入什么内容 |
| 人物设定 | 人设标识、名称、固定前缀 | 决定注入内容里的固定前缀 |

四类在数据上分列,装配时收敛为三份输入:标签集、策略表、人物设定。一份资产包不必四类齐全:它可以只包含其中任意几类,但必须在包内声明包含哪几类,见 2.8。提示词模板依附于策略与人设,内核不为它单设模块;它仍是可独立声明、可独立选择来源的一类内容,只是装配时并入注入文本,不单独作为一份输入。这是有意的:模板一旦独立成模块,就要定义变量、条件与作用域,资产就从「可完整编辑的数据」变成「需要解释的小语言」。

### 2.4 内核不内置具体内容

- 没有默认标签、默认策略、默认人设。内核代码里不存在任何一句会进入系统提示词的文案。
- 没有命中标签且资产未给兜底策略时,各请求参数为空、注入为空,规划结果等于「不改变请求」。插件不因为用户没配置就自行补一套。
- 变化的唯一来源是资产。同一份资产在同一内核版本下的规划结果一致,换一份资产就换一套行为,不需要改插件。

因此不会出现「插件把助手变成某种样子」:插件只提供通道,不提供内容。

### 2.5 一比一导入导出的含义

| 要求 | 含义 | 若不做 |
|:---:|:---:|:---:|
| 字段完备 | 界面可设置项集合等于资产包字段集合 | 出现只有作者能改、用户改不了的属性 |
| 语义保真 | 数值、文本、阈值、优先级按原样往返 | 导出时补默认值或裁剪空白,用户设置被静默改写 |
| 导入即校验 | 失败给出字段路径并整包拒绝 | 部分导入,留下半套资产且无法判断缺了什么 |
| 整体替换 | 导入成功才替换现有资产 | 导入失败后旧资产已被破坏 |
| 预设同格式 | 预设包与用户包走同一套校验 | 预设带特权字段,用户包无法表达同等内容 |

表中「整体替换」只指单次导入写入的原子性:一次导入要么整体生效,要么完全不生效。它不等同于 2.8 排除的「整体替换式导入」,后者指用一个包顶掉用户当前所有类型的来源。

「不存在用户无法设置的属性」是前两条的合并结论:界面能导出完整资产包,资产包能完整导入,于是用户从界面可以到达任意一个合法资产状态。预设包也走同一条路径,导入后就是普通用户资产,可改、可再导出,没有锁定项。

这里有一个成立条件:界面的字段定义与资产包的字段定义必须同源。两处各自手写字段,漂移必然发生,漂移的部分就是用户设置不进去或导出会丢的属性。这条约束直接决定了 4.1 与 4.2 不能分开定稿。

### 2.6 内置资产合集的定位

- dsc-humanize-inner-asset 提供的是可导入的预设资产包,与用户自建包同格式、同校验。
- 它是资产的来源之一,不是内核的一部分:不参与分类,不参与合并,不带特权字段,内核也不认识它的名字。
- 用户不导入任何预设时,插件仍完整可用,只是不改变助手。删掉内置合集不会减少任何能力,只会少几份现成内容。
- 内置合集更新只影响预设内容,不影响内核行为;反过来,内核升级也不改写用户已导入的资产。

因此「插件只支持那几种样子」不成立。预设是起点,不是边界。

### 2.7 边界上的已知取舍

- 注入只能被非空值覆盖。兜底策略里写了注入文本,后续规则无法把它清空。需要「不注入」时应在资产层省略该字段,而不是靠高优先级规则覆盖。理由:合并语义保持只增不减,避免一条高优先级规则意外清掉作者写的兜底文案;代价是无法用空字符串表达「清除」。
- 越界值有两处不同处理:导入校验拒绝越界值,策略解析按边界收敛。正常资产路径先校验后解析,越界值到不了解析;收敛分支只对绕过校验的程序化装配生效。理由:导入要给作者明确错误,解析要保证任何输入都能产出可下发的结果;代价是同一份数据在两处口径不同。
- 规则必须引用已定义的标签,否则整包导入失败。理由:避免策略永远不生效的静默失效;代价是标签改名必须同步改规则。
- 分类器失败不自动降级。分类器抛出即本次规划失败,内核不自行回退到规则分类器。理由:回退等于替装配方选择实现,失败原因会被掩盖;代价是装配方必须显式处理分类失败。
- 类型声明必填,不接受无声明的包。理由:声明是校验与来源选择的唯一依据,放弃它只能靠猜内容;代价是作者要多写一个字段,写错时整包被拒而不是被容忍。
- 同类内容的来源由用户选,内核不设跨包优先级。两个包都提供某一类内容时,取舍在用户侧完成,见 2.9.1。理由:谁覆盖谁没有客观依据,由内核定顺序等于替用户做内容取舍;代价是冲突要用户自己消化,内核不提供仲裁。

### 2.8 按类型声明与按类型组合

资产包不是一个不可分的整体,而是若干类可组合的内容。2.3 的四类内容彼此独立:一个包可以只包含其中任意几类,但必须在包的元数据里声明它包含哪几类。装配时每一类内容各有来源,来源可以取自某个包,也可以是用户自己写的。

| 环节 | 规则 | 若没有这条 |
|:---:|:---:|:---:|
| 声明 | 包元数据必须列出包含的内容类型,不少于一类 | 加载方只能按内容猜,猜错时静默错位 |
| 选择 | 每一类内容的来源由用户分别指定:某个包,或用户自写 | 引入一个包就会顶掉用户在其他类型上的选择 |
| 加载 | 资产加载按类型返回,每个类型附内容与来源标识 | 调用方拿到混合体,无法判断某段内容属于哪一类 |
| 装配 | 装配按类型逐类取来源,合成一份装配输入 | 包内组件无法拆分,跨包无法组合 |

已定约束:

- 类型声明是必填项。缺声明按格式错误整包拒绝,不按内容推断补齐。
- 允许的类型集合固定为 2.3 列出的四类。包不需要四类齐全,也不必保持四类中的任何一类非空。
- 类型集合固定,且与插件流程环节挂钩:分类标签对应分类管线,策略库对应策略解析,提示词模板与人物设定对应注入拼接。开发期可以随插件逻辑扩展类型集合,扩展动作发生在内核版本里;构建成产物之后,用户与资产作者都不能自行扩展。
- 包不能自定义类型。每一类都对应内核里一处具体的装配点,增加一类就是增加一个装配点,属内核版本变更,不是资产能声明的事。包的元数据出现四类之外的标识时按格式错误整包拒绝,不改名、不忽略、不按内容推断。
- 声明与实际内容必须双向一致:声明了某类却没有该类内容、有内容却没有声明,都整包拒绝。理由:声明是校验与来源选择的唯一依据,允许偏差等于让来源选择落在不存在的内容上。
- 引入包不改变用户在其他类型上的选择。导入只作用于包声明、且用户在导入时选定的类型。
- 用户自写内容与包内同类内容地位相同,都只是一种来源;不为自写内容设特权字段或旁路。
- 装配结果必须记录每一类内容的来源标识与版本,使「这次规划用了哪个包的哪一类内容」可回答。

2.5 表中的「整体替换」与本节的关系需要区分清楚:它指单次写入的原子性,导入要么整体生效,要么完全不生效;本节排除的是「整体替换式导入」,即用一个包顶掉用户当前所有类型的来源。前者保留,后者不做。

由此推出两个结论:

- 纯人设包天然合法。只声明人物设定的包不需要为了凑齐四类补空标签集或空策略表:没有标签集就没有命中标签,没有策略表就没有请求参数,注入里只有人设前缀,规划结果是一份只改提示词的规划。只有标签集与策略库的包同样合法,此时注入为空,规划只按策略改参数。
- 包的体量由内容决定,不由格式要求决定。作者的拆分方式都合法:一人设一包、一套策略一包、四类混合包。用户侧的来源选择可以跨包组合。

对内核的影响:

| 影响点 | 改造前 | 改为 |
|:---:|:---:|:---:|
| 资产加载 | 一次加载给出一个包的完整内容 | 按类型返回:每个类型给出内容与来源标识,单个包不再被当作完整配置 |
| 装配输入 | 标签集、策略表、人设取自同一个包 | 每一类分别取来源,来源是当前使用快照里按类型的内容(2.9.3);内容可以来自不同的包,也可以来自用户自写 |
| 校验 | 校验包的完整性,四类是否齐全不影响结论 | 先校验声明,再校验声明与内容一致;四类齐全不再是条件 |
| ONNX 前置条件 | 标签集版本必须与资产包一致 | 仍成立,但比对对象是标签集这一类的来源与版本,而非整包 |

来源选择是装配参数,由调用方传入。内核不认识包的名字,不替用户选默认来源,不缓存来源选择,也不自行跨包合并。同类内容出现多个来源时如何取舍已定,见 2.9.1:取舍在组合时由用户完成,组合结果落进当前使用快照(2.9.3);内核的装配输入是快照里每一类的一份内容,因此合成结果可复现、可对比。

这样定的理由有三条。第一,它是「预设只是来源」(1.3)的自然延伸:来源从「整包」下沉到「某一类内容」,用户才能只取一个人设而不接受作者附带的策略。第二,包内组件可拆分之后,小包比四类齐全的大包更容易审阅,单类内容出错时影响面被限制在一处。第三,声明把「包能提供什么」变成可校验的事实,装配方不需要理解内容语义就能组装,资产作者也不需要知道用户的其他来源。

### 2.9 资产组合的最终规则

2.8 把来源从整包下沉到某一类内容之后,还剩四个问题:两个包都提供同一类内容时谁说了算、组合会不会改动包本身、组合结果存在哪里、类型集合能不能被扩展。四条规则如下。

| 规则 | 含义 | 位置 |
|:---:|:---:|:---:|
| 不设跨包优先级 | 同一类内容被两个包同时提供时,由用户选择其一,或选择两者一起使用并自行处理冲突 | 2.9.1 |
| 资产包只读 | 包在磁盘上不可变;加载进内存之后才允许修改与组合;组合不回写包 | 2.9.2 |
| 当前使用快照 | 单独存一份最后一次使用的组合结果,并记录它涉及哪些包的哪些内部部件 | 2.9.3 |
| 类型集合固定 | 类型与插件流程环节挂钩,产物期用户不可扩展 | 2.8 |

#### 2.9.1 不设跨包优先级

| 环节 | 规则 | 若不做 |
|:---:|:---:|:---:|
| 地位 | 提供同类内容的两个包地位相同,没有隐含顺序、权重或先来后到 | 内核必须替包排序,排序规则一变,规划结果跟着变 |
| 取舍 | 用户选择其一,或选择两者一起使用 | 内核替用户裁决内容,用户只能感到设置被静默改写 |
| 冲突 | 两者一起使用时,冲突由用户自行处理:改内容、去掉其中一份,或接受两者并存 | 内核要做仲裁就必须定义冲突判定与合并顺序,又回到「设优先级」 |
| 追溯 | 组合里的每一次取舍都能追到用户的一次操作,不能追到内核的默认值 | 出了问题无法区分是用户选的还是插件补的 |

已定约束:

- 不存在任何形式的跨包优先级:没有包顺序,没有包权重,没有「后导入覆盖先导入」,也没有「内置包优先」。
- 两个包并存时不报冲突错误,也不自动合并同类内容。「一起使用」的结果就是两份内容同时在场,语义冲突由用户承担;两份内容无法同时成立时(例如两套策略表并置),由用户在组合时就地改成能成立的一份,或只保留其中一份。
- 内核与装配方都不提供冲突裁决。用户不处理冲突时,组合结果里就带着这份冲突,不会被静默消解。
- 冲突如何呈现依赖界面能力,属 4.2 的待定项;本节只定「由谁处理」,不定「怎么呈现」。

理由三条。第一,同类内容之间的取舍是内容判断,不是计算判断:两个作者写的两套策略都可能自洽,谁覆盖谁没有客观依据,内核给顺序等于用默认值替用户做内容决定,与 1.2 的「不承诺固定形象」直接冲突。第二,优先级一旦存在就会成为事实上的推荐:用户不配置时按默认顺序生效,冲突静默发生,只表现为「设置没生效」,用户说不出哪里被改了。第三,把冲突交给用户,2.5 的一比一导入导出才有意义:包的内容与用户的选择各归各位,不互相污染。

#### 2.9.2 资产包只读

| 环节 | 规则 | 若不做 |
|:---:|:---:|:---:|
| 存储 | 包在磁盘上不可变:导入、组合、装配都不改写包文件 | 同一个包在不同用户、不同次数下字节不同,无法比对与校验 |
| 加载 | 加载进内存之后才允许修改与组合,内存副本是组合的工作区 | 只能就地改包,包一旦被用过就不再是作者发布的内容 |
| 回写 | 组合结果不回写资产包,也不被写进任何包 | 导出与分发的基准被本地使用状态污染 |
| 归属 | 包的更新只由作者与合集产生,用户侧的改动只存在于内存副本与当前使用快照 | 用户改动的来源无法区分,升级时不知道该保留哪一边 |

已定约束:

- 包是只读来源:内核加载包时只读,组合方修改的是内存副本,不改包。
- 组合不回写:一次组合结束,磁盘上的包与组合前逐字节相同。
- 导出资产包时导出的是包自身的内容,不是组合结果;组合结果只存在于当前使用快照(2.9.3)。
- 「包」与「用户当前在用的东西」是两件事:前者只读、可分发、可校验,后者可变、属于用户。

这样定的理由:只读是让「来源」这个概念成立的前提。包一旦会被组合改写,「同一个包」就不再指同一份内容,哈希、索引、合集校验与用户之间的交换都失去基准;而组合本身又必须可变,否则用户无法在别人的包上做自己的调整。把可变部分整体挪到内存副本与快照上,两件事才能同时成立。

#### 2.9.3 当前使用快照

当前使用快照存放最后一次使用的组合结果,也就是当时实际参与装配的内容。它是独立的一份存储,不在任何资产包里。

| 项 | 规则 | 若不做 |
|:---:|:---:|:---:|
| 内容 | 存当时实际使用的内容本身,不存来源清单 | 只存来源清单时,包一更新,「当时用的什么」就无法还原 |
| 来源记录 | 记录这份快照涉及哪些资产包的哪些内部部件:按包、按部件留痕 | 只能回答「用过哪些包」,回答不了「这段内容出自哪个包的哪一类部件」 |
| 完整性 | 快照是一个整体,不把它切分成多块再单独标注来源 | 切块后每块都要独立来源与合并顺序,等于在快照之上再造一层来源选择与优先级,回到 2.9.1 已排除的做法 |
| 唯一输入 | 装配只读快照,不读包,不做跨包合并 | 装配同时面对包与快照时,两处内容谁生效无法回答 |
| 独立性 | 包更新不自动改写已存在的快照,换不换新版包由用户重新组合决定 | 上游一改,用户当前在用的行为跟着变,而且没有留痕 |
| 边界 | 快照不写回包,也不是包的一部分 | 包变成可变的,2.9.2 的只读前提失效 |

已定约束:

- 快照的内容粒度是「当时实际的内容」,不是「当时的包列表」。记录来源是为了回答「从哪来」,不是为了把内容拆开分别挂来源。
- 来源记录以部件为单位:哪个包、包内哪一类部件、该部件的版本。同一类内容在组合里用了两个包时,两份来源都记,不合并、不排先后。
- 快照里每一类只有一份内容,这一份可以由多个部件的拼接构成;装配参数从快照取,内核不感知快照内部来自几个包。
- 快照始终对应「最后一次使用」,因此重新组合是整体替换:旧快照被新快照整体取代,不做逐类增量修改,也不把新旧快照拼在一起。
- 快照的物理载体是 IndexedDB(4.6),逻辑上仍是「一份完整快照 + 部件来源记录」;库名与版本、清理策略与导出路径尚未定稿,本节只定它的内容、来源记录与只读关系。在 IndexedDB 通道落地前,插件存储承担一份过渡快照的读写,键名与形状见 4.6,标注为可调整。

这样定的理由:用户实际在用的东西,与作者发布的包,是两份不同的数据。前者要回答「上一次到底是什么在生效」,后者要回答「这个包原本是什么」。把两者混在一份存储里,任何一次包更新都会改写「上一次」,任何一次组合都会改写「原本」;分开之后,包的只读与组合的可变互不影响,出问题也能分别核查。

#### 2.9.4 四条规则合起来的样子

| 步骤 | 发生在 | 产物 | 对包的操作 |
|:---:|:---:|:---:|:---:|
| 导入 | 用户侧 | 磁盘上的只读包 | 只读 |
| 组合 | 用户侧,在加载后的内存副本上进行 | 一份组合结果,即当时的实际内容 | 只读,不回写 |
| 落盘 | 用户侧 | 当前使用快照:内容本身,加来源部件记录 | 不涉及 |
| 装配 | 内核 | 一次规划:意图、策略、注入 | 不读包,只读快照 |

四条规则互相咬合:只读让包成为稳定的来源,不设优先级让取舍留在用户手里,快照让「上一次实际在用什么」可回答,类型集合固定让这三件事在格式上有确定的边界。缺一条,另外三条都会退化成需要重新论证的约定。

对内核的影响:

| 影响点 | 改造前 | 改为 |
|:---:|:---:|:---:|
| 装配输入 | 调用方直接传入某个包的标签集、策略表与人设 | 传入当前使用快照中按类型的内容 |
| 来源概念 | 一个包就是一次装配的完整来源 | 快照才是装配来源,包只是快照内容的出处 |
| 包的读写 | 加载后直接使用包的内容 | 加载只读;组合在内存副本上做,回写禁止 |
| 冲突处理 | 无,单来源时不存在冲突 | 不在内核;内核收到的每类内容已由用户组合好 |

组合与快照写入由内核之外的装配方完成。内核只读快照,3.6 的纯计算性质因此不变:同一份快照、同一段文本、同一组装配参数,得到同一份规划。

### 2.10 资产生态的信任

本插件同时属于两个生态,身份不同。两个身份都真实存在,但结论不能互相借用:混用是这套信任最容易出错的地方。

| 生态 | 本插件的身份 | 由谁签发 | 信任锚 |
|:---:|:---:|:---:|:---:|
| ds-chat 插件生态 | 一个第三方插件 | 组织内部插件合集的 EEC 证书 | ds-chat 自己的根证书 |
| dsc-humanize 资产生态 | 根 CA,签发资产合集 | 自签根证书 | 本仓库 `certs/dsc-humanize/dsc-humanize-root-ca.crt` |

资产侧只有两级,没有中间 CA:

| 层级 | 证书 | 主题 | 签发者 | 约束 |
|:---:|:---:|:---:|:---:|:---:|
| 第一级:根 CA | `certs/dsc-humanize/dsc-humanize-root-ca.crt` | `O=omds-chat, CN=dsc-humanize ROOT CA` | 自身(自签) | `CA:TRUE`、`pathlen:0`,仅证书签发与 CRL 签发 |
| 第二级:资产合集 EEC | `certs/<来源 id>/<来源 id>-eec.crt` | `CN=<来源 id>` | 第一级的根 | `CA:FALSE`,仅数字签名,不能再签发 |

公开材料按来源文件夹存放,一个来源一个目录:

| 路径 | 内容 | 用途 |
|:---:|:---:|:---:|
| `certs/dsc-humanize/` | `dsc-humanize-root-ca.crt`、`dsc-humanize-root-ca-secret.pub` | 资产侧唯一信任锚,以及核对根密钥对的公开材料 |
| `certs/dsc-humanize-inner-asset/` | `dsc-humanize-inner-asset-eec.crt`、`dsc-humanize-inner-asset-eec-secret.pub` | 内置资产合集的证书与其公钥 |
| `certs/awesome-dsc-humanize-asset/` | `awesome-dsc-humanize-asset-eec.crt`、`awesome-dsc-humanize-asset-secret.pub` | 社区资产合集的证书与其公钥 |

`*-secret.pub` 是 `*-secret` 私钥推导出的公钥,可以直接公开;私钥本身不进本仓库。

已定约束:

- 两条链互不隶属。ds-chat 根证书不能用来验资产来源,本仓库的资产根也不能用来验插件产物。理由:两个信任域的根、签发者与失效时间各不相干,借用一边的结论等于让一次校验通过建立在另一套主体的判断上;更根本的是被验对象不同,资产是用户导入的纯数据,插件是可执行产物,准入条件本就不同(2.1)。
- 资产来源的验签只认一个锚:`certs/dsc-humanize/dsc-humanize-root-ca.crt`。锚在仓库里,不在网络上:不从页面下发的链里临时取根,不信任任何外部地址提供的根,校验方的结论因此与上游页面的当前状态无关。
- 锚随构建内嵌:构建时读取 `certs/dsc-humanize/dsc-humanize-root-ca.crt`,把 PEM 注入为产物常量;文件缺失或不是 PEM 证书时构建失败。只内嵌公开证书,根私钥不进仓库也不进产物。内嵌回答的是「运行时手上有没有锚」,不回答「验签怎么做」:签名覆盖范围与校验失败是否阻断仍属 4.4。
- 一个来源只有一份公开材料。消费方引用路径,不复制字节;复制到别处,更新时必然留下两份不同步的根,「哪一份是锚」不再有答案。
- 仓库只放公开材料:根证书、各 EEC 证书与其公钥。根私钥与任何 EEC 私钥都不进本仓库,也不随插件产物分发;私钥由各来源自己持有,签发发生在本仓库之外。
- 插件生态里的身份不受影响:资产根不参与插件合集的签发,插件证书轮换也不改变资产链。两条链各自演进,互不牵制。
- 本节只定身份、链的形状与锚点。资产签名覆盖哪些字段、由作者还是合集签、校验失败是否阻断,仍属 4.4 的待定项,本节不为其中任何一种可能背书。

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 用 ds-chat 根证书当资产来源的锚 | ds-chat 根签发的是插件合集,没有为资产背书;这样验签会把「插件合集被认可」误当成「资产来源被认可」 |
| 用本仓库的资产根去验插件产物 | 反向混用同样错位:资产根只签发资产合集 EEC,`pathlen:0` 也说明它不建更长的链 |
| 由页面或索引下发根证书,校验时随用随取 | 根随内容走,校验方读到的根就可能与本地锚不同,信任结论变成由分发方决定 |
| 多个仓库各存一份根,各自更新 | 根一旦分叉,同一个来源在不同校验方得出不同结论,也无法判断哪一份权威;锚只能有一处 |
| 把根私钥或 EEC 私钥放进仓库,便于复现签发 | 私钥入库等于把签发能力交给所有能读仓库的人;公开侧只含证书与公钥 |

## 三、内核模块划分

### 3.1 模块与职责

| 模块 | 职责 | 输入 | 输出 | 纯计算 |
|:---:|:---:|:---:|:---:|:---:|
| 分类管线 | 文本到按置信度排序的标签,过滤阈值以下的结果 | 文本、标签集、阈值、取消信号 | 标签、主标签、分类器标识 | 规则实现是;模型实现待定 |
| 策略执行 | 标签到一条收敛后的策略 | 策略表、分类结果、置信度下限 | 各请求参数、命中标签、策略表版本 | 是 |
| 注入拼接 | 人设前缀与注入文本到最终片段 | 前缀、注入文本、已有提示词、位置、分隔符 | 提示词、加入数、丢弃记录 | 是 |
| 资产读取 | 资产包到按类型划分的内容,并完成校验 | 资产引用、读取通道 | 按类型返回的内容与来源标识,或错误码 | 校验是;取字节由通道完成 |
| 装配 | 串起上述三段,产出一次规划 | 当前使用快照中按类型的内容、分类器、位置 | 意图、策略、注入、来源记录 | 是 |
| 资产交付 | 激活时读当前使用快照,或导入一份资产包文档,把内容交给装配 | 插件存储、资产包文档 JSON | 按类型的内容,或读取错误 | 否,读写插件存储 |

「策略执行」在本文指解析与合并,不指把参数发到请求上。落地是宿主的职责,见 4.3。

### 3.2 分类管线

- 分类器只做文本到标签的映射,只能输出资产标签集里出现过的标识;输出出现标签集之外的值视为实现错误。
- 结果按置信度降序,同分按标签标识排序,保证同一输入得到同一顺序,便于回放与比对。
- 阈值缺省 0.3,低于阈值的标签不进入策略解析;标签权重缺省 1。
- 规则实现按关键词命中数量给分,命中越多置信度越高,按标签权重缩放并收敛到 1;未命中的标签不返回。
- 规则实现同时给出同步入口,与异步入口共用同一套打分与阈值;宿主的请求前回调是同步的,那里只能用同步入口。
- 分类器可替换,装配时由调用方选择。策略与注入不感知分类器种类,只消费标签结果。

### 3.3 策略执行

- 合并顺序:先兜底策略,再按优先级升序合并命中的规则;优先级相同按声明顺序;后合并的值覆盖先前的值。
- 策略表可以只给兜底策略:规则数组为空时不合并任何规则,兜底策略照常生效。
- 注入文本只被非空值覆盖;停止词去空白、去空串、去重并保持首次出现的顺序。
- 数值边界:temperature 为 0 到 2,topP 为 0 到 1,maxTokens 为 1 到 32768 的整数,越界按边界收敛。
- 未命中任何规则时仍应用兜底策略;兜底策略也没有时各字段为空,由宿主决定「不改变请求」。
- 解析结果带命中标签与策略表版本,用于回答「这次响应由哪版资产的哪些规则产出」。
- 内核只判断取值是否在声明范围内,不判断「这组值对某个模型是否合理」。后者属于资产作者的判断,内核不替它兜底。

### 3.4 注入拼接

- 片段顺序固定:人设前缀、策略注入文本、注入类型的片段依次排列;注入类型内部的片段顺序由装配参数给出。
- 丢弃三类片段:空串;内容重复(忽略连续空白差异);内容已出现在已有提示词中。
- 位置缺省追加到已有提示词之后,可选前置;片段之间的分隔符可配置,缺省两个换行。
- 只拼接文本,不解释语义、不裁剪长度。提示词预算由资产作者与宿主承担,内核不因为「太长」而静默删减。

### 3.5 资产读取

- 读取单元:资产包在磁盘上是一个目录(元数据加若干已声明的类型目录),内核一次只读一份文本,因此由调用方把目录扁平化成一份加载期包文档:元数据原样放进 `metadata`,各类型目录的条目按类型分组放进 `contents`。文档与目录一一对应,不是另一种资产格式,目录形态仍是格式的权威形态。
- 两条路径:本地数据直接校验;地址经调用方注入的读取通道取回后按 JSON 解析。
- 本地交付有两条入口,都不改变内核的装配参数:插件激活时从插件存储读取当前使用快照(键名与形状见 4.6,标注为可调整);界面落地前由 `importAssetPackage` 从 JSON 文本导入一份加载期资产包文档。两条入口都复用本节的逐类读取器校验,读出的内容再交给装配。
- 两条入口的写入语义不同:导入必须先通过整包校验,成功后才整体替换当前使用的内容,失败时旧内容保持不动;激活读快照失败时保持空内容,不阻断激活,也不做部分保留。没有快照时装配输入为空,请求保持原样。
- 宿主侧的读取通道只对内置插件开放,第三方插件拿不到任何网络能力,远端资产因此当前不可用,见 4.5。
- 读取按类型返回:一次加载给出包声明的类型、每一类的来源标识(包标识与包版本)与条目,单个包不视为完整配置。加载只读,不改写包内容;跨包组合由装配方完成,结果落在当前使用快照里,内核不做跨包合并,见 2.8 与 2.9。
- 声明与内容双向一致:声明了某类却给不出条目、给出空集合,或有内容却没声明,都整包拒绝;类型声明为空、重复、出现四类之外的标识同样拒绝。每个声明的类型至少一个条目,条目在同一类型内标识唯一。
- 包内策略的标签引用:包声明了标签集时,规则的标签必须落在包内的标签集里;没有声明标签集时,引用留待装配阶段由标签集来源解析。
- 内核自身不发网络请求。没有提供通道时,地址资产以「通道缺失」失败,由调用方决定降级方式。
- 失败分四类:通道缺失、通道失败、内容不是合法 JSON、结构或取值不合法。结构错误带字段路径,便于直接定位到出问题的属性。
- 失败以结果对象返回,不抛错。降级方式(回退到本地资产、回退到纯文本、提示用户)属于调用方,内核不替它选。
- 校验只覆盖内核消费的字段与判定:格式版本、包标识与版本、类型声明与各类型条目;名称、说明、署名、许可证等展示字段不进入读取结果。字段是否封闭、内容标识的词法规则由资产包格式的校验脚本负责;两侧口径不一致时以格式规范为准,见 4.1。

### 3.6 纯计算性质

| 约束 | 含义 | 理由 |
|:---:|:---:|:---:|
| 不读宿主 | 不访问会话、设置、插件存储 | 行为只由输入决定,内核可脱离宿主测试与复用 |
| 不写宿主 | 不落盘、不改请求、不改提示词 | 落点是宿主的责任,内核越过边界就无法保证契约 |
| 不发网络 | 地址资产由调用方注入通道 | 插件能力受宿主约束,内核不假设自己有网络 |
| 不吞错误 | 资产失败返回结果,分类失败抛出 | 降级策略属于装配方,内核替它决定会掩盖失败 |
| 不改输入 | 不修改传入的资产内容 | 同一份资产可被反复规划,结果可复现、可对比 |

纯计算不是风格偏好,而是这条链路能被验证的前提:规划结果只取决于文本、资产与装配参数,不取决于「刚才发生过什么」。

### 3.7 ONNX 分类器现状

- 接口已固定:模型地址、标签集版本、置信度阈值;分类器标识带模型地址,规划结果里能看出是哪个模型产出的标签。
- 接口已固定并处于占位状态,没有推理实现。在推理实现接入前,classify 一律拒绝,并给出「回退到规则分类器」的提示。
- 不返回猜测结果。理由有三条:标签直接驱动策略与注入,错误标签会静默改变助手行为;置信度阈值由资产设置,资产可以把阈值调低,于是「低质量猜测」也会被放大成实际策略;拒绝能让失败显式暴露,装配方可以选择降级而不是带着错误结果继续。
- 标签集版本必须与提供该标签集的来源一致;标签集与模型来自同一个包时,这条等价于与资产包一致。模型输出映射到另一套标签,比没有标签更危险:看起来生效了,实际语义已经错位。
- 接入的前置条件:确定推理运行时与依赖;模型随资产分发并在加载前校验地址与版本;文本预处理与分词规则与训练配置一致,且写进资产;支持取消,并给出首次推理的预热与失败降级策略。这些是接入条件,不是内核行为。

在内核视角,ONNX 与规则分类器可以互换:装配方选哪个,规划结果就带哪个分类器标识。策略与注入不因分类器不同而走不同分支。

### 3.8 资产交付与信任锚内嵌

交付层位于内核之外:它读写插件存储与日志,把内容交给装配;内核仍只接收 3.1 定义的按类型内容,纯计算性质不变(3.6)。

| 项 | 当前做法 | 边界 |
|:---:|:---:|:---:|
| 激活装配 | 读取插件存储里的当前使用快照,校验通过才替换内存中的内容 | 没有快照或快照不合法时保持空内容,只写日志,不阻断激活 |
| 显式导入 | 从 JSON 文本读取一份加载期资产包文档,整包校验通过后整体替换并写回快照 | 校验失败时旧内容与旧快照都不动;写快照失败时内存装配仍生效,由返回值标明未持久化 |
| 根证书 | 构建时读取 `certs/dsc-humanize/dsc-humanize-root-ca.crt`,以常量注入产物,运行时导出 PEM | 只内嵌公开证书;证书缺失或不是 PEM 时构建失败;内嵌不等于已实现验签 |

根证书内嵌只保证「锚在产物里」:资产签名覆盖哪些字段、由谁签、校验失败是否阻断仍属 4.4 的待定项,本节不为其中任何一种可能背书。验签实现接入前,运行时不应把「有锚」当成「已校验」。

## 四、未定稿

六节里,4.1、4.2、4.4 与 4.5 尚未定稿;4.3 的宿主能力与映射规则已定,只余用户可见性。未定稿各节按「已知约束、待定问题、已排除做法」写;4.5 另加「为什么现在不做」一段,说明它与哪些尚未落定的契约互相牵制。4.6 的存放介质已定为 IndexedDB,过渡实现的键名与形状、库内细节、清理策略与导出路径未定。已排除的做法不再重提,避免下一个人重新论证一遍。

### 4.1 资产包格式与加载期包文档

已知约束:

- 包的目录布局、元数据字段与四类内容字段由 dsc-humanize-asset-template 的规范 1.0.0 定义,本仓库不另立格式;内核只约定读取时消费的字段与加载期包文档的形状,见 3.5。
- 资产包必须在元数据里声明包含哪几类内容;缺声明、声明与内容不一致都按格式错误整包拒绝,见 2.8。
- 一个包可以只包含四类中的任意几类,允许的类型集合固定,纯人设包合法。
- 引入包不整体替换用户当前配置:每一类内容的来源由用户分别选择,来源是某个包或用户自写。
- 导入即校验:标签标识唯一;包内声明标签集时规则引用的标签必须存在;每条规则至少给出一个策略字段;数值在声明范围内;人物设定的标识、名称、前缀齐全。
- 格式版本是必填的三段数字,当前 1.0.0;格式规范要求加载方拒绝主版本不同的包,内核读取尚未比较主版本。
- 资产包必须能承载界面里的每一个属性,且导出后能原样导入。
- 包本身只读、组合不回写、组合结果落在当前使用快照,见 2.9.2 与 2.9.3;格式定稿不得引入需要改写包字段的机制。
- 同类内容跨包时的取舍已定,见 2.9.1:不设跨包优先级,由用户选择其一或两者并用;冲突由用户自行处理。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 加载期包文档是否固定为「元数据加按类型内容」 | 它是目录包的一次读取投影;是否随导入通道(文件、文本、地址)变化,取决于 4.2 的导入方式 |
| 内核支持的格式主版本范围 | 格式规范要求加载方拒绝主版本不同的包;内核读取当前不比较主版本,支持范围随内核版本策略与升级路径定 |
| 导入导出路径与打包分发形态 | 取决于合集与索引如何收资产,以及用户导入的是文件、文本还是地址 |
| 文本编码、换行与大小上限 | 取决于导入通道与存储方式 |
| 编辑器字段定义与资产字段的同源方式 | 取决于界面实现方式,决定由哪一侧生成校验规则 |
| 用户自写内容存在哪里、是否也要声明类型 | 取决于 4.2 的存储取舍与打包分发形态;若自写内容与包走同一套校验,它就是独立文件,否则只能作为装配状态的一部分 |

「同一类型出现多个来源时如何合并与解决冲突」一项已由 2.9 定稿,不再作为本节待定项:取舍由用户完成,内核不设优先级。仍待定的只剩冲突如何呈现,它依赖 4.2 的界面能力。

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 直接把内核的类型定义当对外格式 | 类型是实现的内部形状,改实现就破坏用户资产;格式需要独立版本与稳定边界 |
| 复用插件清单或插件包格式承载资产 | 插件是可执行产物,资产是数据;混用会把执行、权限与安装生命周期带进资产,「一比一导入导出」会被插件版本牵制 |
| 允许资产携带可执行脚本或模板表达式 | 资产必须能被界面完整编辑并静态校验;可执行内容无法保证一比一往返,也把内容问题变成代码审计问题 |
| 无 Schema 的自由 JSON,字段全部可选 | 给不出字段级错误,也无法保证「不存在用户无法设置的属性」 |
| 多套格式并存、导入时静默迁移 | 迁移必然改写用户资产,与一比一冲突;版本不兼容应显式报错,由用户决定是否转换 |
| 整体替换式导入:导入一个包即顶掉用户当前所有类型的来源 | 用户的配置是多来源合成的,整包替换会静默清掉用户自写与其他包的内容,用户只能感到「设置有东西丢了」;也与 1.3 的「预设只是来源」和 2.5 的一比一冲突 |
| 包不带类型声明,由加载方按内容猜测类型 | 四类里存在判断不唯一的情形(人设前缀与提示词模板都是文本),猜测结论随启发式改动而变化,同一份包在不同版本下归类不同,猜错还静默生效;声明是校验与来源选择的前提 |
| 用「缺省即包含四类」的隐式声明 | 会凭空造出空的标签集与空策略表,而「选了空集合」与「没有这一类」在装配时是两种含义,混在一起就无法区分用户是清空了还是没选 |
| 组合时回写资产包,或把当前使用快照存进包内 | 包一旦随使用变化,同一个包就不再指同一份内容,哈希、合集校验与用户之间的交换都失去基准;也违反 2.9.2 的只读前提 |
| 给包排顺序或用「后导入覆盖先导入」消解同类冲突 | 顺序是内核替用户做的内容取舍,用户看不到也改不动,与 1.2 的「不承诺固定形象」冲突;见 2.9.1 |

### 4.2 编辑界面

已知约束:

- 宿主当前的能力表里没有界面插槽类能力,插件只能通过提示与日志与用户交互。界面落在哪里,受宿主能力约束。
- 插件存储有单插件容量上限,且清除站点数据即丢失,不能作为资产的唯一副本。
- 一比一导出要求界面字段与资产字段同源,不能各写一套。
- 界面必须覆盖资产包的每一个属性,包括长文本、数值、枚举与列表。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 界面落点 | 取决于宿主是否开放插槽,以及插件面板是否允许承载编辑视图 |
| 字段分组与校验提示 | 取决于资产格式的字段全集 |
| 预览方式 | 是否展示拼接后的提示词、是否展示命中标签,取决于宿主是否提供请求上下文 |
| 来源与冲突的呈现 | 同类内容来自两个包并一起使用时,界面上如何标出冲突、由用户在何处处理,取决于格式(4.1)与界面能力;取舍由谁做已定,见 2.9.1 |
| 导入导出交互 | 取决于资产打包形态,以及宿主是否允许文件读写 |
| 资产存放位置 | 文件、插件存储还是浏览器本地数据库,取决于容量与生命周期要求;当前使用快照(2.9.3)不得落在资产包内,其介质已定为 IndexedDB(4.6) |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 只提供预设选择器,不提供逐项编辑 | 与「不存在用户无法设置的属性」直接冲突,预设只能是起点 |
| 用一个 JSON 文本框作为唯一编辑界面 | 技术上能设置每一项,但没有字段级校验与说明,普通用户无法使用,与「由用户在插件界面输入与编辑」不符 |
| 界面自建一套字段模型,导出时再映射 | 两套模型必然漂移,漂移的部分就是用户设置不进去或导出丢失的属性 |
| 把资产存进插件存储当作唯一副本 | 容量不足,且随站点数据清除而丢失;资产应以文件形式由用户持有 |
| 由插件改写宿主页面结构来造界面 | 越过插件契约,宿主改版即失效,也会干扰其他插件 |

### 4.3 宿主能力:改请求参数与系统提示

宿主能力已具备(`chat:request`),映射规则见本节。

已知约束:

- 内核只产出策略与提示词片段,不执行。策略字段与请求参数同名,是「可被落地的形状」,不是「已经落地」。
- 形态为拦截式:清单申请能力 `chat:request` 并声明挂载点 `chat:before-request` 后,插件在激活时通过 `context.chat.onBeforeRequest` 登记处理器;引擎在每次发请求前同步调用一次,把补丁写进请求参数,插件不提交独立策略、也不持有请求对象。
- 请求切片只有 `lastUserMessage`,拿不到已有系统提示词、历史消息与工具参数。
- 插件拿不到 API Key,也不能读取附件原件与其他插件的数据。
- 系统提示词与请求参数属于宿主与用户的会话内容,改动必须可解释、可追溯。

映射规则:

| 内核结果 | 宿主字段 | 收敛 |
|:---:|:---:|:---:|
| `strategy.temperature` | `temperature` | 引擎按 0 到 2 裁剪 |
| `strategy.topP` | `topP` | 引擎按 0 到 1 裁剪 |
| `strategy.maxTokens` | `maxTokens` | 引擎按 1 到 4096 裁剪;内核边界为 1 到 32768,差值由引擎收敛 |
| `strategy.stop` | `stop` | 引擎按最多 4 条、每条最多 32 字符截断 |
| `injection.prompt` | `systemPromptAppend` | 引擎按最多 2000 字符截断,追加到现有 `system` 之后 |

- 只给宿主支持的字段,不给 `systemPromptReplace`:切片里没有系统提示词,整体替换会丢掉宿主自己的内容。
- 插件不自行裁剪数值与长度:内核只判断取值是否在资产声明范围内,越界与超长交给引擎按补丁上限收敛,两处各管一段。
- 没有标签集或策略表时返回 `null`,不改请求;分类器抛错或资产不合法时同样返回 `null`,只写插件日志,不阻断请求。
- 注入以空串为已有提示词起点,由宿主追加;内核的注入位置 `prepend` 只在能拿到完整系统提示词时才有意义,当前不用。
- 多个插件同时登记时由引擎按登记顺序合并:标量以后登记者为准,`stop` 取并集并在 4 条处截断,追加提示词按顺序拼接后按长度截断。
- 与 dsc-llm-tune 互斥:两者都改写同一次请求的参数,同时安装时补丁会按登记顺序互相覆盖,用户无法预测最终取值,因此本插件清单声明 `conflicts: ['dsc-llm-tune']`,对侧清单声明本插件,只改一侧等于没有互斥。职责互补但不并存:本插件按资产给预设,dsc-llm-tune 让用户自由调节参数,按需切换而不是同时安装。`meta.json` 里的同名字段只求与清单一致,宿主由 `meta.json` 推导清单时不读它。
- 处理器同步执行,全部处理器共用 10 毫秒预算;超时或抛错时整份补丁作废,请求按原参数发出。

仍待定:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 用户可见性 | 引擎只在超时与越界时各提示一次;是否在界面标注「本次请求由某资产改写」,以及标注粒度,取决于宿主的界面能力 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 插件自行请求上游接口 | 需要 API Key,而插件按契约拿不到;也越过宿主的会话、计费与错误处理 |
| 改写用户消息正文来模拟系统提示词 | 污染会话内容,用户无法区分自己写的与插件加的,还会被历史记录固化 |
| 直接改写全局请求函数或页面内的请求对象 | 破坏宿主契约,影响其他插件,宿主改版即失效 |
| 在宿主没有入口时按假设的接口先写死调用 | 假设的接口一旦不同就是死代码,还会让资产作者误以为能力已存在 |
| 申请网络能力绕过宿主 | 该能力只对内置插件开放;即使可申请,也只能取字节,不能改请求 |
| 在插件里再裁剪一遍补丁 | 与引擎的收敛重复,两侧边界迟早漂移;插件按内核结果原样给出,越界交给引擎 |

### 4.4 资产生态信任体系

已知约束:

- 资产是纯数据,由用户导入;导入后的效果完全取决于内容,不取决于它来自哪里。
- 资产有两个来源:内置合集与社区合集。两者都只是索引与分发,不是内核的一部分,内核不认识来源。
- 组织在插件体系里已有证书链与来源校验;资产生态不沿用这套链,两者是独立信任域(2.10)。
- 身份与锚点已定,见 2.10:本插件在插件生态里是一个插件,在资产生态里是自签根 CA;资产来源的验签以本仓库 `certs/dsc-humanize/dsc-humanize-root-ca.crt` 为唯一锚,该根与 ds-chat 根证书无关。本节只处理签名覆盖范围、签名者与结论呈现这些仍待定的部分。
- 资产包只读(2.9.2):包在磁盘上不可变、组合不回写,因此一份包的校验结论与它交付给用户的内容始终对应。
- 资产会被用户之间交换,同一份包在不同用户处的行为应当一致。

待定问题:

| 问题 | 为什么不能单独定 |
|:---:|:---:|
| 资产是否签名、签名覆盖哪些字段 | 取决于资产打包形态与是否允许部分更新 |
| 签名者是谁:作者还是合集 | 取决于合集在生态里的角色,是只做索引还是同时托管与背书 |
| 信任结论如何呈现 | 需要先定义结论的几种状态,以及界面能承载的信息量 |
| 失败时是否阻断 | 组织在插件体系里的现行口径是校验失败只警告、不阻断;资产是否沿用需要明确 |
| 资产更新与撤回 | 已导入的资产如何得知上游变化,是否需要撤回机制 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 以人工逐包审核作为唯一准入 | 无法扩展,审核结论也不可机器验证,用户仍无法判断手里的包是否被改过 |
| 把资产当可执行产物做代码签名与执行沙箱 | 资产是数据,没有执行语义;引入沙箱只增加复杂度,不增加实际保障 |
| 由中心化白名单垄断分发 | 与「预设只是来源之一」冲突;用户应能导入自建或第三方资产 |
| 运行时从任意地址自动拉取并信任资产 | 未经用户确认的远端内容会直接改变助手行为;地址可达不等于内容可信 |
| 以「未签名」本身作为拒绝加载的理由 | 与组织现行的「只警告、不阻断」口径相反,也会把信任问题变成可用性问题 |

### 4.5 远端资产能力

已知约束:

- 插件不是内置插件。宿主能力表里的 `net:fetch` 只对内置插件开放:第三方插件的清单声明它时按未知能力拒绝,调用层再校验一次。因此 3.5 的地址路径没有通道可用,远端资产通道当前不可用。
- 内核不发网络请求(3.6):地址资产由调用方注入通道取回,内核只做 JSON 解析与校验。通道存不存在不改变内核的形状。
- 若做,候选形状是宿主新增一条受控的资产读取能力,不是开放通用网络:只允许 https,不带凭证(不附带 Cookie、Authorization 与自定义请求头),限体积与超时,首次访问某个地址时需用户确认。
- 跨域是否放行由对方服务器决定:浏览器发出的请求能否读到响应体,取决于对方的响应头;静态站点通常没有配置,插件侧无法绕过,也不能靠改地址或换协议绕过。
- 探测结论只能三态:取到内容;读到明确的错误状态码,说明对方已放行、只是该地址的内容不对;无法判定。第三态无法区分「地址无效」与「对方未开启跨域」,提示文案固定为「该链接无效或对方未开启跨域访问」。
- 新增一条对插件可见的能力,要同时进能力联合、可见集合、服务注册、引擎策略表与两处规范副本;限流窗口与超时由引擎侧统一,口径与既有能力同源。

候选:

| 候选 | 形状 | 代价 |
|:---:|:---:|:---:|
| 宿主新增受控资产读取能力 | 只允许 https、不带凭证、限体积与超时、首次地址需用户确认的单动作能力 | 属于新增能力,要与能力表、限流契约一起定;跨域仍由对方服务器决定,三态里最坏的一态只能给出合并文案 |
| 维持本地导入 | 资产包由用户下载到本地后导入,远端地址只作为获取入口的提示 | 没有一键使用远端资产的能力;合集与索引只能引导用户自行下载,地址失效时也没有插件侧的探测 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 在清单里申请内置插件的那条取字节能力,或复用内置插件的通道 | 该能力只对内置插件开放,申请会被拒;绕过等于越过能力契约,「能力由宿主授予」这条前提也随之失效 |
| 插件自行请求任意地址 | 把网络暴露面从「一个受控动作」扩大到「任意源」,而资产是纯数据,不需要这种表达力 |
| 用公共跨域代理中转请求 | 代理能看到资产内容,信任面从对方服务器挪到第三方;代理的可用性也不由我们控制 |
| 把「无法判定」一律报成地址无效,或一律报成对方未开跨域 | 两种原因在浏览器侧无法区分,单报一种会把用户引到错误的排查方向;文案必须同时覆盖两种可能 |
| 探测成功就把该地址记为可信来源 | 地址可达不等于内容可信,信任结论属 4.4;探测只回答「这次能不能读到字节」 |

为什么现在不做:

- 这条能力的形状要与引擎侧的「唯一 core 调用通道」与限流契约一起定:资产读取只是新增能力的一个用例,先按资产的需要定一条网络形状,等通道与限流口径落定后就要返工。
- 三态探测的失败分支直接决定 4.2 的界面文案与导入流程,而界面落点尚未定;先定能力会把文案与流程锁在未定的界面上。
- 跨域不受我们控制:先做也只能覆盖一部分托管方式,结论随托管方式而变,不适合当成统一定稿。

### 4.6 当前使用快照的存放位置

已定结论:快照存放在 IndexedDB,不占 localStorage 的配额。宿主对单插件 localStorage 数据的 64KB 上限保留原位,继续用于插件的小体量配置。过渡实现期间(见下文的「已落地的过渡实现」)快照暂存在插件存储里,这是已知的临时例外,不是对这条结论的修改。

已定约束:

- 介质:快照整份写进 IndexedDB,一次写入完成整体替换,与 2.9.3 的「重新组合即整体替换」对齐;不做逐类增量写入。
- 配额分工:插件的小体量配置仍走插件数据(localStorage),快照不进插件数据,两者不共用同一份额度。过渡实现把快照暂存在插件存储里,属下文标注的可调整项,不是对这条分工的修改。
- 上限不动:`dsc-core/plugin-data.ts` 的 `MAX_DATA_BYTES` 保持 64KB,不按写入内容分档。这份上限由宿主自己定,不是浏览器或存储介质的限制,放宽它只改宿主侧的常量,但影响面覆盖全部插件。
- 快照仍不是资产的唯一副本:IndexedDB 也在浏览器本地,清除站点数据即丢失,资产以导出的包为准(4.2)。

已落地的过渡实现(可调整):

在 IndexedDB 通道接入前,插件先从插件存储读取一份快照,让「有内容可装配」这条链路可验证。这组键名与形状先定一版,标注为可调整:

| 项 | 当前取值 | 说明 |
|:---:|:---:|:---:|
| 读取介质 | 插件存储,即 `plugins:storage` 的 `context.storage` | 只作为过渡入口;4.6 的已定结论仍是 IndexedDB,不因这条路径改变 |
| 存储键名 | `dsc-humanize/snapshot/v1` | 24 字符,在宿主「非空且不超过 64 字符」的键名约束内;改名属于可调整项 |
| 快照形状 | `{ "snapshotVersion": 1, "contents": { <类型>: { "source": { "id": "...", "version": "..." }, "items": [ ... ] } } }` | `contents` 是 2.9.3 的「内容本身」;每类的 `source` 是部件来源记录的最小形态,更细的部件记录随 4.1 与 4.2 调整 |
| 版本字段 | `snapshotVersion`,当前为 1 | 不等于 1 时整份拒绝,不静默迁移;升级路径留给界面落地时定 |
| 读取时机 | 插件激活时读一次 | 之后的请求只读内存中的内容;重新组合或重新导入后不需要重新激活 |
| 写入时机 | `importAssetPackage` 导入成功后整份写入 | 与 2.9.3 的「整体替换」一致,不逐类增量写入 |
| 缺快照或不合法 | 保持空内容,请求不改变,只写插件日志 | 不做部分保留;激活时以快照为准,先清空内存内容再装配,之后的替换由 `setActiveContents` 与导入入口负责 |
| 写入失败 | 内存装配仍生效,返回值标明未持久化 | 64KB 上限撞线时先丢持久化,不丢当前这次装配 |

这组取值可调整,原因是它同时受三处未定稿牵制:4.1 的字段全集决定 `source` 与条目字段的最终形状,4.2 的导入方式决定写入时机,IndexedDB 的库内约定(下节「未定的部分」)决定键名与版本号是否还要保留。调整它只影响插件存储里的这一份快照,不影响资产包格式,也不影响 2.9.3 的语义,因此可以先用一版把链路打通。

还要说明两点边界。第一,插件存储的 64KB 上限意味着快照只能容纳小体量组合;撞线时导入仍会装配,只是写不进存储,下次激活回到旧快照或空内容。第二,这条路径不是把 4.6 的介质结论改回 localStorage:它只是过渡期的一条最小交付入口,IndexedDB 落地后键名与形状可以整体搬过去,也可以直接废弃。

两条依据:

| 依据 | 说明 |
|:---:|:---:|
| localStorage 配额留给普通插件数据 | 64KB 是宿主对单个插件的插件数据上限,对全部插件同时生效,而插件数据要装的是开关、阈值、界面偏好这类小体量配置。快照是组合后的完整内容,与配置不是同一类数据:两者共用一份额度时,配置的可用空间随快照大小波动,先撞线的是配置 |
| 快照体量不可预期 | 快照存的是「当时实际使用的内容本身」(2.9.3),内容来自多个包,文本量由资产作者决定,本插件无法预估也无法裁剪。把不可预期的字节数放进固定上限的存储,撞线只是时间问题;而撞线发生在整份替换时,表现是写不进去、旧快照原样留着,用户看到的是「组合没生效」 |

未定的部分:

| 项 | 待定内容 | 为什么现在不能定 |
|:---:|:---:|:---:|
| IndexedDB 内的库名与版本 | 库名、对象仓库怎么划分、schema 版本号与升级方式 | 仓库划分取决于快照的记录形状:内容与来源记录分仓还是同一条记录,随 4.1 的字段全集与 4.2 的字段定义定稿 |
| 过渡快照的键名与形状是否沿用 | `dsc-humanize/snapshot/v1` 与 `{ snapshotVersion, contents }` 搬到 IndexedDB 后是否原样保留 | 取决于库内记录如何划分;若内容与来源分仓,键名与版本号会被库内约定取代 |
| 清理策略 | 旧版本对象的删除时机、浏览器回收存储后的降级表现 | 与 4.2 的资产存放位置同源;快照丢失后是提示重建还是静默重组合,取决于界面是否给出重建入口 |
| 导出路径 | 快照以什么形态导出、是否与资产包同一条出口 | 导出通道未定(4.2);快照带来源记录,与只读包的导出不是同一形态(2.9.2),两者不能共用一份格式 |

已排除的做法:

| 做法 | 理由 |
|:---:|:---:|
| 把快照切块分存,只留来源清单 | 违反 2.9.3 的完整性:切块后每块都要独立来源与合并顺序,等于在快照之上再造一层来源选择与优先级 |
| 把快照存进资产包,或随包一起分发 | 违反 2.9.2 的只读前提:包一旦随使用变化,同一个包就不再指同一份内容,哈希与合集校验失去基准 |
| 压缩后写进插件数据以规避上限 | 上限按字节计,压缩只把撞线往后推;快照仍要整份解出才能装配,压缩也破坏了「字节相同即内容相同」的比对 |
| 为快照单独申请一条宿主存储能力 | 浏览器本地数据库已能承载,新增能力要进能力表与限流契约(4.5);为省掉一层库名约定而扩大宿主对插件的能力面,代价大于收益 |
| 只存与某个基准包的差异,靠增量还原 | 增量依赖基准,基准一更新差异就失效,快照不再自足,与 2.9.3 的独立性冲突 |
| 不持久化,每次启动重新组合 | 需要重新读包并重新组合,「最后一次使用」不再是用户的选择记录,2.9.3 要回答的问题随之消失 |
