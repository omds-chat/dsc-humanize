# 人性化资产市场

> 本文固定人性化资产市场的形态、来源模型、取件与信任顺序、安装语义、更新与卸载、失败与降级口径,以及它与插件自身能力的关系;仍未定稿的项逐条列在第八节,并附已排除的做法。
> 本文只写机制、边界与取舍理由:不写实现代码,不写界面细节(界面落点属未定稿),也不复述资产包格式。
> 资产包的格式、字段与校验顺序由 dsc-humanize-asset-template 的规范 1.0.0 定义;内核与资产的分工见 [内核与资产](kernel-and-assets.md),本文只消费其中的结论。

## 一、形态

### 1.1 市场是插件界面里的一个入口

三句话把形态定死:

- 市场不单独建站。它不是站点、不是页面工程,没有自己的域名与入口地址。
- 市场没有独立仓库。它随 dsc-humanize 的产物一起分发,源码在本插件的源码树内。
- 市场不发布 Pages。它不从任何自有地址分发索引、清单或资产包。

市场在插件界面里只做三件事:管理来源、浏览来源的包目录、管理已安装的包与更新。具体落在哪个面板、以什么形态呈现,属未定稿(第八节),不影响上述三条。

| 决定 | 理由 | 若不做 |
|:---:|:---:|:---:|
| 不建站 | 索引与包由合集分发,市场只是消费方;另立站点会出现第二份「谁分发什么」的事实 | 站点索引与合集索引必然分叉,分叉后无法判断哪一份是准据 |
| 不设独立仓库 | 市场的全部依赖是内核的校验与装配、宿主的读取通道、合集的索引 | 多一个仓库就多一条发布链路与一套版本对齐成本,而它没有任何独立交付物 |
| 不发布 Pages | 市场没有需要公开的内容:它不发包、不签清单、不做信任锚 | Pages 会让人误以为市场也是来源,与「来源只有合集」直接冲突 |

### 1.2 与插件市场的关系

DeepSeek-Chat-Enhanced 内置的插件市场(`dsc-market`)是本文的形态参照:它的来源列表、多地址兜底、信任判定、安装计划与失败提示这套结构被整体沿用。但两者不是同一个东西,也不共享来源列表:

| 维度 | 插件市场 | 资产市场 |
|:---:|:---:|:---:|
| 安装对象 | 可执行产物 `plugin.js` | 纯数据资产包 |
| 信任锚 | ds-chat 根证书 | 本仓库 `certs/dsc-humanize/dsc-humanize-root-ca.crt` |
| 谁判定 | 宿主引擎按本地链与验签判定 | 本插件自己做链校验与验签 |
| 来源归属 | 插件来源进插件市场的内置列表 | 资产来源不进插件市场的列表,只在本文定义的来源列表里 |

两条链互不隶属是已定约束(见 [内核与资产](kernel-and-assets.md) 2.10),因此「把资产来源挂到插件市场里」不只是界面归属问题,而是会让一次插件生态的结论被当成资产来源的结论。

### 1.3 已排除的做法

| 做法 | 理由 |
|:---:|:---:|
| 建独立站点或独立仓库承载市场 | 市场没有独立交付物;站点会与合集索引分叉 |
| 把资产来源并入插件市场的来源列表 | 两个信任域,结论不能互相借用 |
| 由合集页面提供浏览与下载 | 合集侧已明确不设展示站点,重复一套只会分叉 |
| 在插件里再维护一份资产索引 | 同一事实两处维护;市场按合集索引取件即可 |

## 二、来源

### 2.1 来源的标识:URL 加合集 id

一个来源由两部分组成,缺一不可:

| 部分 | 作用 | 为什么不能省 |
|:---:|:---:|:---:|
| 一组 `base_url` | 决定从哪里取件:索引、清单、证书、包内文件都相对它拼路径 | 地址是配置,换镜像或换托管只改这里,不动其他任何字段 |
| 合集 id | 决定取哪张证书(`certs/<合集 id>/<合集 id>-eec.crt`),也决定信任结论归属到谁 | 只有地址时,同一地址换个目录就能自称另一个来源;只有 id 时,取件位置无从拼起 |

合集 id 的取值规则与合集目录名一致:小写字母开头,只含小写字母、数字与连字符,长度 3 到 64。它同时是来源的标识符:同一合集 id 只能有一条来源,新增重复 id 时拒绝,理由是同 id 两条来源会共用同一张证书,结论无法归属。

### 2.2 内置来源

内置两条,列表顺序即默认优先级:

| 来源(合集 id) | 定位 | `base_url` 顺序 |
|:---:|:---:|:---:|
| `dsc-humanize-inner-asset` | 组织自研的预设资产包 | `https://omds-chat.github.io/dsc-humanize-inner-asset/` |
| `awesome-dsc-humanize-asset` | 社区投稿的资产包 | `https://cdn.jsdelivr.net/gh/omds-chat/awesome-dsc-humanize-asset@main/`、`https://raw.githubusercontent.com/omds-chat/awesome-dsc-humanize-asset/main/`、`https://omds-chat.github.io/awesome-dsc-humanize-asset/` |

- 单条来源内的多个 `base_url` 按顺序尝试,单次请求短超时,失败自动切下一个。
- 内置来源不可删除,但可以改 `base_url` 列表与顺序。理由:地址属于部署事实,合集换托管时用户不该被迫等插件升级;而「有没有这条来源」属于产品事实,不该被用户配置改掉。
- 本地联调地址由构建注入,注入值非法时退回线上地址。地址判定与信任校验不分开发与线上:注入值同样要过 2.5 的地址判定,本地地址不享受任何例外。
- 两个内置来源地位相同:都只由根证书签发的 EEC 证明身份,没有哪一条因为「内置」而跳过校验(见 3.4)。

### 2.3 用户自建来源

用户可新增、删除、排序自建来源,规则与内置来源同形:

| 规则 | 内容 |
|:---:|:---:|
| 必填项 | 合集 id、至少一个 `base_url` |
| 地址判定 | 与插件来源判定同口径,见 2.5 |
| id 冲突 | 与已有来源(含内置)同 id 时拒绝新增 |
| 校验 | 与内置来源完全一致:先校链再验签,不因为自建而降低要求 |
| 结论 | 没有「未在清单登记」这一档:链与验签都通过就是来源已确认 |
| 改 id | 等于换来源:安装记录保留,更新检查按新 id 重新取证书 |

用户自建来源与内置来源的差别只有两条:内置的默认存在、不可删除;其余一律相同。这与「预设只是来源」的定位一致:来源不因出处获得特权字段,也不因自建而被另眼看待。

### 2.4 来源配置的存放

来源配置写入插件存储的一个键,值为 `{ sources: [...] }`,每条含 id、名称、`baseUrls`、是否内置。结构不符时整体退回内置默认值,不做部分保留。

目录缓存不写进插件存储:宿主对单插件的存储上限是 64KB,大目录会把这份额度挤满,先撞线的会是来源配置这类小体量数据。这条取舍与插件市场一致。

### 2.5 地址判定

允许 `https://` 任意主机,或 `http://` 的回环地址(`localhost`、`127.0.0.1`、`[::1]`);写入前统一去掉查询与哈希,并补齐尾部斜杠。

理由只有一条:这套判定与引擎的插件来源判定同口径。两套地址规则会让同一份配置在一处合法、在另一处非法,排查时无法判断是配置错还是规则差异。

### 2.6 不设来源白名单

资产侧没有「官方登记清单」这一层:

| 判断 | 依据 | 结论 |
|:---:|:---:|:---:|
| 来源是否被认可 | 证书链能否用本仓库的资产根校验通过 | 能过链即被这套 PKI 认可,不需要额外名单 |
| 来源是否被推荐 | 不在判定里 | 顺序只表示默认优先级,不表示可信度 |

插件市场里那份信任清单属于插件生态的策略层,资产侧不沿用:资产侧只有一个锚(2.10 已定),锚在仓库里、由本插件内嵌,「根签发了它」就是全部答案。多一层名单只会让「同一份证书在两处得到不同结论」成为可能。

## 三、取件顺序与信任

### 3.1 取件顺序

对每个来源,按下面的固定顺序执行;每一步失败时的处理在最后一列。除第十一步与「宿主没有读取通道」之外,前面任何一步失败都不阻断浏览,只降级结论:

| 序 | 动作 | 取用位置 | 失败时 |
|:---:|:---:|:---:|:---:|
| 1 | 取来源元数据 | `<base_url>meta.json` | 切下一个 `base_url`;全部失败即来源不可达 |
| 2 | 取合集证书 | 三档,见 3.2 | 拿不到证书:来源结论判为未通过(证书缺失),目录仍展示 |
| 3 | 在插件内校验证书链 | 本插件内嵌的资产根 | 链不通过:来源结论判为未通过,且**不发起**清单验签 |
| 4 | 识别分发模型 | `manifest.json` 加 `assets.json`;或 `web_files.json` 加证书 | 两者都不成立:按未确认处理,签名结论一律未校验 |
| 5 | 验来源级清单签名 | 合集模型 `manifest.json` 加 `manifest.json.sig`;整站模型 `web_files.json` 加 `web_files.json.sig` | 验签不通过:签名结论失败,来源结论判为未通过,目录仍展示 |
| 6 | 校验清单覆盖文件的哈希 | 合集模型 L1 覆盖 `meta.json`、`assets.json`、`tags.json`、`assets/author_manifest.json` | 哈希不一致:签名结论失败,来源结论不变,目录仍展示 |
| 7 | 取包列表 | `<base_url>assets.json` | 结构不符:目录为空并提示索引不可读 |
| 8 | 取作者层清单 | `assets/<作者>/asset_manifest.json` 及其签名 | 只影响该作者名下的包 |
| 9 | 取包层清单 | `assets/<作者>/<包标识>/manifest.json` 及其签名 | 只影响该包 |
| 10 | 取版本信息 | 该包目录的 `versions.json`(合集模型由 L3 清单覆盖) | 只影响该版本 |
| 11 | 安装时取包内全部文件 | 按 L3 清单列出的路径逐个取 | 整包拒绝,不落盘(见 4.3) |

三条约束:

- 三步的先后固定:先取证书与清单,再用本插件内置的资产根校链,最后验清单签名。链不过时不发起验签,但清单照常用于展示。
- 同一来源的信任材料必须同址取用。不允许把 A 地址的签名与 B 地址的证书拼在一起,否则「这份签名证明的是谁」不再有答案。
- 逐层取件,不用聚合索引。合集侧已明确聚合索引不进任何清单、不参与验签;市场若依赖它,一旦与清单不一致,拿到的摘要就无法用于校验。

### 3.2 证书与链

| 档 | 地址 | 说明 |
|:---:|:---:|:---:|
| 1 | `certs/<合集 id>/<合集 id>-eec.crt` | 公开发布布局,两个内置来源都用这一档 |
| 2 | `certs/<合集 id>-eec.crt` | 扁平布局,只作兼容 |
| 3 | `eec.pem` | 根目录布局,整站签名的来源常见这一档 |

- 信任锚是本插件内嵌的 `certs/dsc-humanize/dsc-humanize-root-ca.crt`,不从页面或其他索引取根。根随内容走,校验结论就由分发方决定。
- 三档都由本插件用内置根校链;链不通过时不再发起清单验签。理由:验签只能回答「字节与签名一致」,不能回答「签名者是谁」,链是后一个问题的唯一答案。
- 证书不进任何清单的覆盖面,也不进资产包:证书是校验的输入,列进清单会出现「清单由证书签、证书又由清单担保」的循环。

### 3.3 两种分发模型

两个内置合集的发布形态不同,市场按特征文件识别,识别顺序固定:

| 模型 | 特征文件 | 签名材料 | 结论覆盖 |
|:---:|:---:|:---:|:---:|
| 合集模型 | `manifest.json` 与 `assets.json` 都取到 | 每层一份 `manifest.json` 加 `manifest.json.sig` | 逐层:来源级(L1)与包级(L3) |
| 整站模型 | `web_files.json` 且证书已取到 | `web_files.json.sig` 加逐文件 `<文件>.sig` | 逐文件,按本次实际消费的文件验签 |
| 未确认 | 两种特征文件都不成立 | 无 | 目录照常展示,签名结论一律未校验 |

- 合集优先是硬约束:整站模型不改变合集模型的取件与结论,只在合集特征文件不成立时介入。
- 逐文件验签的对象是市场已取到的那份字节,不重新取件,避免验签内容与实际消费内容不一致。
- 整站清单只在首次消费时验签一次,结论在同一次目录拉取内复用。

### 3.4 签名结论与来源结论

两个轴各回答一个问题,互不替代,也不能由一侧推断另一侧:

| 轴 | 回答 | 取值 | 判定依据 |
|:---:|:---:|:---:|:---:|
| 签名结论 | 这份字节与签发时是否一致 | 通过、未校验、失败 | 清单签名验签结果,加清单覆盖文件的哈希比对 |
| 来源结论 | 这份内容是否出自该来源 | 已确认、未通过、无法确认、本地 | 本地证书链校验,加清单签名验签 |

取值条件:

| 情形 | 签名结论 | 来源结论 |
|:---:|:---:|:---:|
| 链通过、验签通过、哈希一致 | 通过 | 已确认 |
| 链通过、验签通过、某文件哈希不一致 | 失败 | 已确认 |
| 链通过、验签不通过 | 失败 | 未通过 |
| 链不通过 | 未校验(不发起验签) | 未通过 |
| 拿不到证书 | 未校验 | 未通过(证书缺失) |
| 两种模型特征都不成立 | 未校验 | 已确认或未通过,按链的结论 |
| 用户本地导入的包,没有来源 | 不适用 | 本地 |

两个细节:

- 第二行与第三行的区别是有意的:验签不通过说明签名不属于该来源,来源结论跟着降级;哈希不一致说明签名是对的、被签的字节被换过,来源本身仍成立。把两者压成同一个结论,排查时无法区分「身份不对」与「内容被改」。
- 两个结论都随安装记录落盘,且每次安装重新计算,不采信记录里的旧值。旧值可能来自更早的语义,直接采信会让同一次失败在两次安装里得到不同结论。

来源结论的作用只有一个:告诉用户「这份内容确实出自这个来源」。它不决定能不能装:签名与来源失败一律只提示、不阻断(见 6)。

### 3.5 失败不阻断的边界

「只提示不阻断」只约束签名与来源这两条轴。有一条线在它之外:包读不了。

| 类别 | 例子 | 处理 | 理由 |
|:---:|:---:|:---:|:---:|
| 内容可疑但可读 | 链不通过、验签失败、哈希不一致、索引未校验 | 提示并允许安装 | 组织现行口径:签名与信任失败只警告,由用户判断 |
| 读不了 | 格式主版本不同、元数据不是合法 JSON、声明与内容不一致 | 拒绝安装 | 这不是「信不信」的问题,是内核读不出内容;装了也不会生效 |

这两类必须分开:把「读不了」也说成「只提示」,用户会得到一份装了但不生效的包;把「可疑」也拒绝,就把信任问题变成了可用性问题。

## 四、安装语义

### 4.1 安装做什么,不做什么

安装一个资产包 = 把包内容导入本地,并让它成为按类型组合的候选。它不覆盖任何已有内容:

| 动作 | 发生什么 | 不做什么 |
|:---:|:---:|:---:|
| 校验 | 按资产包规范的顺序整包判定 | 不做部分导入,不静默补默认值 |
| 落盘 | 写入一份本地只读副本,按来源、作者、包、版本分层落位 | 不改写包,不把使用状态写进包 |
| 登记 | 写一条安装记录,含来源、版本、类型集合、两个结论 | 不改用户在其他类型上的选择 |
| 参与组合 | 该包声明的类型各自多出一个候选来源 | 不自动成为某个类型的当前来源,不设默认来源 |

三条已定结论在此处落地:

- 同一类型出现多个来源时由用户选择,内核不设跨包优先级(见 [内核与资产](kernel-and-assets.md) 2.9.1)。市场不替用户排顺序,也不提供「合并同类内容」的动作。
- 包是只读来源,组合在内存副本上进行,结果落进当前使用快照(2.9.2 与 2.9.3)。市场只负责把包放到位,不参与组合。
- 引入包不改变用户在其他类型上的选择。这一点是安装与「整体替换式导入」的分界:后者已被排除。

### 4.2 本地副本

| 项 | 规则 |
|:---:|:---:|
| 定位 | 副本按「合集 id / 作者 / 包标识 / 版本」落位,同名包来自不同来源时互不覆盖 |
| 只读 | 副本与来源的字节一致;导入、组合、装配都不改写它 |
| 与快照的关系 | 副本是「作者发布的包」,快照是「用户最后一次在用的内容」,两份数据分开存 |
| 版本并存 | 同一包的不同版本各存一份,升级不就地覆盖旧版本 |

### 4.3 原子性与失败

安装是整包的:一次安装要么整体生效,要么完全不生效。

| 阶段 | 失败时的处理 |
|:---:|:---:|
| 取件(第 11 步) | 不落盘,已有副本与记录保持不变 |
| 整包校验 | 不落盘,给出字段路径 |
| 写入副本 | 写入中断时删除半成品,不登记安装记录 |
| 登记 | 登记失败时删除已写入的副本,回到安装前的状态 |

理由:半套资产比没有资产更糟。用户无法判断缺了什么,而界面会把半套当成一套展示。

### 4.4 安装记录

一条安装记录要能回答四件事:从哪来、是什么、信不信、用什么。

| 字段 | 内容 | 用途 |
|:---:|:---:|:---:|
| 来源 | 合集 id、本次实际生效的 `base_url` | 更新检查、追溯 |
| 包 | 作者、包标识、版本、格式版本 | 与本地副本一一对应 |
| 类型集合 | 包声明的四类中的哪几类 | 组合时只在这些类型上出现候选 |
| 结论 | 签名结论与来源结论,各带原因 | 界面展示与排查 |
| 清单修订号 | 各层清单的 revision | 回退提示 |
| 时间 | 安装时间 | 排序与「最近安装」 |

## 五、更新与卸载

### 5.1 更新检查

| 环节 | 做法 |
|:---:|:---:|
| 对象 | 只对来自在线来源的包做;本地导入的包不参与 |
| 最新版本 | 取该包目录的 `versions.json`,读 `latest` |
| 判定 | 本地记录版本落后为「可更新」,相同或更高为「已是最新」,版本号不合法则不显示任何标注 |
| 请求约束 | 单请求短超时、并发上限 4、失败静默、结果缓存 5 分钟 |

失败静默的边界:更新检查不产生来源结论,也不改签名结论。它只是一个提示,拿不到就什么也不显示,不把「查不到最新版」写成「已是最新」。

### 5.2 更新不动用户的编辑

「包更新保留用户的编辑」不是靠合并实现的,而是靠两者本来就不在一处:

| 数据 | 归属 | 更新时 |
|:---:|:---:|:---:|
| 资产包副本 | 作者 | 新版本装成新副本,旧版本保留 |
| 内存副本上的组合 | 用户 | 组合结束即写进快照,包更新不触碰 |
| 当前使用快照 | 用户 | 包更新不改写它;换不换新版由用户重新组合决定 |

因此更新只有一条路径:按新版本重新走一遍取件与整包校验,装成新的版本副本,并更新安装记录。旧快照继续生效,界面上「有更新」与「当前在用哪一版」是两个独立的提示。

这条规则也解释了为什么包内不能有「默认人设」这类字段:一旦包能表达默认值,更新就会静默改变用户看到的行为。

### 5.3 卸载

| 动作 | 删除 | 保留 |
|:---:|:---:|:---:|
| 卸载一个包 | 该包的全部版本副本、该包的安装记录 | 用户自写内容、当前使用快照、其他包的副本与记录 |
| 卸载一个来源 | 该来源本身与其配置 | 从该来源装过的包与它们的记录(来源被标注为已移出列表) |

- 卸载不清用户自写内容:自写内容本来就不在包里,卸载动作也不触碰它。
- 卸载不改快照:快照存的是内容本身加部件来源记录(2.9.3),包被删后快照仍完整可装配,来源记录仍能回答「这段内容原出自哪个已卸载的包」。
- 清理入口不在卸载里。要清掉用户数据,走设置里的数据管理,并明确告知后果。

### 5.4 已下架清单

合集可以发布一份已下架清单,位置固定为 `<base_url>catalog/removed.json`,用于在用户取不到某个包时区分「曾经有、后来下架」与「从来没有」:

| 结论 | 条件 | 表现 |
|:---:|:---:|:---:|
| 已下架 | 命中任一条目 | 提示该包已不再由该来源分发,建议关注其他来源;不删除本地副本、快照与记录 |
| 不存在 | 至少一份清单可达但未命中 | 沿用「未找到这个资产包」的提示 |
| 未判定 | 清单全部不可达,或市场尚未就绪 | 沿用原有的取件失败提示,不作判断 |

只有「取不到包」这一类失败才触发查询;签名与链不通过不查清单。判定只读:只发 GET 请求,不写来源配置、安装记录与包副本。

## 六、失败与降级

### 6.1 逐项表现

| 情形 | 表现 | 提示口径 | 是否阻断安装 |
|:---:|:---:|:---:|:---:|
| 来源所有地址都不可达 | 来源状态失败,目录为空 | 该来源的所有地址都无法访问 | 无包可装,不影响其他来源 |
| 单个地址失败 | 切下一个地址 | 不单独提示 | 否 |
| 跨域被拒或没有响应 | 三态里的「无法判定」 | 该链接无效或对方未开启跨域访问 | 否,该地址视为不可用 |
| 拿不到证书 | 来源结论判为未通过,原因记为证书缺失 | 来源证书缺失 | 否 |
| 证书链不通过 | 来源结论判为未通过,不发起验签 | 来源证书校验未通过 | 否 |
| 清单验签不通过 | 签名结论失败,来源结论判为未通过 | 清单签名未通过 | 否 |
| 清单哈希不一致 | 签名结论失败,来源结论不变 | 索引数据与清单不一致 | 否 |
| 两种模型特征都不成立 | 结论一律未校验 | 索引数据未校验 | 否 |
| 格式主版本不同 | 包读不了 | 该资产包的格式版本与当前插件不兼容 | 是 |
| 合集声明的格式版本高于本插件支持 | 来源级提示,逐包判定 | 该来源按格式 x 分发,当前插件支持 1.y | 否 |
| `assets.json` 结构不符 | 目录为空 | 资产索引不可读 | 否 |
| 单个包的元数据或版本信息失败 | 该包标记失败 | 该包的数据读取失败 | 否,其余包不受影响 |
| 清单修订号回退 | 来源追加一条提示 | 索引修订号回退到 x | 否,只警告 |
| 宿主没有读取通道 | 所有取件步骤都返回通道缺失 | 当前宿主未提供远端读取通道 | 是,没有可用路径 |

页面安装的成败提示走宿主为资产包新增的成对文案键:成功是 `pluginAssetInstalled`(资产包 {id} 安装完成),失败是 `pluginAssetInstallFailed`(资产包 {id} 安装失败:{reason});只发气泡,不弹窗、不遮罩,失败也不影响其他条目。

### 6.2 降级次序

读取失败时按下面的次序退:

| 次序 | 数据来源 | 何时使用 |
|:---:|:---:|:---:|
| 1 | 本地副本与安装记录 | 展示已安装、可装配内容;任何时候都可用 |
| 2 | 内存中的目录缓存 | 5 分钟内重复进入同一来源 |
| 3 | 来源在线取件 | 缓存缺失或强制刷新时 |

来源全部不可达时,市场仍展示已安装的包与它们的状态,不把空目录写成「没有任何资产」。这条与「失败不阻断」是同一条原则的两面:状态要可读,动作才可判断。

### 6.3 提示文案的三条硬要求

| 要求 | 原因 |
|:---:|:---:|
| 不把「无法判定」说成地址无效 | 浏览器侧区分不了「地址错」与「没开跨域」,单报一种会把用户引到错误的排查方向;固定文案必须同时覆盖两种可能 |
| 不把「未校验」说成「失败」 | 未校验是「没有可比对的材料」,失败是「比对了且不一致」;混用会让可用的来源被当成不可信 |
| 不跨轴表述 | 签名失败不等于来源不可信,来源失败也不等于内容被改过;两个轴各自给结论,不合并成一句「校验未通过」 |

文案落在哪里属未定稿:插件当前的提示能力只能使用宿主已有的文案键,承载不了来源列表与逐条结论(见 7.1)。

## 七、与插件自身能力的关系

### 7.1 需要哪些宿主能力,现在是否具备

| 能力 | 用途 | 现状 | 后果 |
|:---:|:---:|:---:|:---:|
| 远端读取 | 取来源元数据、证书、清单与包内文件 | 已具备:宿主提供 `assets:read`,只 GET、只 https 与回环 http、不带凭证、上限 512KB、超时 10 秒,结果三态(内容/状态码/无状态码)原样返回,限流 20 次 / 10 秒;清单申请即用。`net:fetch` 仍只对内置插件开放,不用于资产取件 | 市场取件经宿主受控通道进行;通道缺失时所有取件步骤返回通道缺失(见 7.2 的保留口径) |
| 插件存储 | 存来源配置与安装记录 | 已申请:清单能力声明含 `plugins:storage`,当前还用于读取过渡快照(4.6) | 可用于来源配置与安装记录,受 64KB 上限约束 |
| 浏览器本地数据库 | 存包副本与当前使用快照 | 已在设计上定为快照的介质,包副本同源 | 可用;库名、版本与清理策略未定稿 |
| 界面落点 | 承载来源列表、目录、已安装与提示 | 不具备。宿主能力表里没有界面插槽类能力 | 入口位置与提示形态未定稿 |
| 一次性提示 | 安装完成等单点提示 | 具备,但只能使用宿主已有的文案键 | 只能承载一句话,不能承载来源列表与逐条结论 |
| 内嵌信任锚 | 校验证书链 | 已具备:构建时从 `certs/dsc-humanize/dsc-humanize-root-ca.crt` 读取 PEM 并注入产物常量 | 锚点可取得;证书链验证、签名覆盖范围与失败是否阻断仍待 4.4 定稿 |

### 7.2 远端读取缺失的后果

> 状态注记:宿主的受控资产读取能力(`assets:read`)已按 7.3 首选候选落地,远端读取不再是硬约束;本节保留,作为「宿主回退到没有该能力的旧版,或通道被移除」情形的后果口径。

这一条必须先解决,后果要写清楚,不能靠假设绕过:

| 后果 | 具体表现 |
|:---:|:---:|
| 市场停在「配置加本地导入」 | 来源列表可以配置、可以排序,但任何取件动作都在第一步失败,返回通道缺失 |
| 三态探测无法进行 | 没有请求就没有响应,跨域那句固定文案没有触发场景;它属于通道具备之后的失败口径 |
| 链与验签仍可对本地包做 | 本地包没有来源材料,来源结论只能在「本地」与「无法确认」之间取值 |
| 不得按假设接口先写死调用 | 假设的接口一旦不同就是死代码,还会让资产作者误以为远端能力已经存在 |
| 不影响内核形状 | 内核按通道取字节,通道由装配方注入;通道不存在不改变内核的模块划分与纯计算性质 |

### 7.3 候选

| 候选 | 形状 | 代价 | 判断 |
|:---:|:---:|:---:|:---:|
| 宿主新增受控资产读取能力 | 只允许 https、不带凭证、限体积与超时、首次访问某个地址需用户确认的单动作能力 | 属新增能力,要同时进能力联合、可见集合、服务注册、引擎策略表与两处规范副本;跨域仍由对方服务器决定 | 已落地:宿主能力 `assets:read` 按此形状实现(https 与回环、无凭证、512KB、10 秒、三态结果);「首次访问确认」未进入宿主实现,以首次使用来源的宿主提示代替 |
| 维持本地导入 | 资产包由用户下载到本地后导入,来源地址只作获取入口的提示 | 没有一键安装;地址失效时没有插件侧探测 | 兜底,市场仍能展示来源与地址 |
| 插件内置化 | 把本插件变成内置插件,直接拿到那条取字节能力 | 插件生命周期绑到主线发版;为一项能力改写插件身份 | 已排除,见 7.4 |

### 7.4 已排除的做法

| 做法 | 理由 |
|:---:|:---:|
| 在清单里申请 `net:fetch`,或复用内置插件的通道 | 该能力只对内置插件开放,申请会被拒;绕过等于越过能力契约 |
| 插件自行请求任意地址 | 把网络暴露面从「一个受控动作」扩大到「任意源」,而资产是纯数据,不需要这种表达力 |
| 用公共跨域代理中转 | 代理能看到资产内容,信任面从对方服务器挪到第三方,可用性也不由我们控制 |
| 把「无法判定」一律报成地址无效 | 与 6.3 冲突:两种原因在浏览器侧无法区分,单报一种会误导排查 |
| 探测成功就把地址记为可信来源 | 地址可达不等于内容可信;信任结论只由链与验签给出 |

## 八、未定稿

### 8.1 待定项

| 项 | 现状 | 为什么现在不能定 |
|:---:|:---:|:---:|
| UI 形态 | 已按 ui:page 落地,宿主插槽细节以引擎文档为准(入口:插件面板 → 插件页面 → 资产市场;来源管理与目录浏览已接入,安装动作与失败降级随页面落地) | 已安装列表与更新入口本轮未纳入页面,仍待编辑界面的落点(内核文档 4.2);确认态、冲突呈现与文案位置都依赖落点 |
| 索引格式复用还是新定 | 复用合集现有索引(见 8.2),不另立格式 | 两个内置合集的元数据字段不一致,统一属合集侧变更;市场先按兼容读取,再由合集侧定统一形状 |
| 缓存位置 | 目录缓存建议只在内存、5 分钟;包副本与快照在浏览器本地数据库 | 是否把目录缓存也落库以支持离线浏览,取决于离线可用的产品意图,以及与快照库内细节(4.6)的联动 |
| 安装入口的数量与共用方式 | 已收敛:市场安装、本地导入共用 `importAssetPackage` 的整包校验与原子语义,各入口只在取件方式上不同;安装记录同形,含来源标识与版本 | 本地导入通道属内核文档 4.2 的未定稿项:入口的界面落点仍未定,但记录与校验的共用方式不再悬而未决 |
| 冲突的呈现 | 已定取舍,留 UI:同一类型多个来源时由用户选择,呈现形态随界面落点实现 | 取舍由谁做已定(2.9.1),怎么呈现依赖界面能力;本轮只到逻辑层,不呈现 |

### 8.2 索引格式:复用的部分与已知不一致

| 项 | 现状 | 处理 |
|:---:|:---:|:---:|
| 包目录索引 | 两个合集都是 `assets.json`:顶层数组,字段为包标识、作者、标签、类型集合 | 直接复用 |
| 版本与包内文件 | 包目录的 `versions.json` 由包层清单覆盖;作者站点侧另有 `files` 字段供合集拉取 | 直接复用 |
| 清单模型 | 一个内置合集用三层清单加逐层签名,另一个用整站清单加逐文件签名 | 市场按两种模型识别,见 3.3 |
| 合集元数据字段 | 一个写成 `assetSpecVersion` 与 `assetFormatVersion`;另一个写成 `name`、`indexVersion` 与嵌套的 `assetFormat` | 读取时两种形状都认;统一由合集侧决定,市场不猜 |
| 规范版本出处 | 上游规范仓库的 `spec-version.json` 用的是 `spec_version` 与 `format_version` | 以该文件为准;合集侧的字段是它的副本,不一致时按 8.1 的「兼容读取」处理 |

这一节的作用是留痕,不是裁决:市场侧能做的只有兼容两种形状,字段是否统一属于合集仓库的变更,不能由市场单方面改。

### 8.3 未定稿项的配套排除

| 做法 | 理由 |
|:---:|:---:|
| 为目录另立一份聚合索引 | 聚合索引不进清单、不参与验签,与清单不一致时拿不到可用于校验的摘要;合集侧已明确它不是消费入口 |
| 把来源配置写进资产包 | 配置属于用户,不属于包;写进包会破坏包只读与一比一导出 |
| 把目录缓存写进插件存储 | 64KB 会被大目录挤占,先撞线的是来源配置这类小体量数据 |
| 用界面自建一套目录模型再映射 | 两套模型必然漂移,漂移的部分就是显示错位或取件失败 |

## 九、与收录条款的关系

inner 合集的收录条款写明资产包「不自行发起任何网络请求」,与本插件的资产 URL 装载之间存在一次外部审计指出的表面矛盾。这一节把两者的契约边界写清楚,只回应、不改条款:措辞是否澄清由 inner 合集侧自行决定。

| 项 | 内容 |
|:---:|:---:|
| 条款的本意 | 「不自行发起任何网络请求」针对的是插件绕开宿主自建通道直连:用全局 `fetch`、`XMLHttpRequest` 或其他方式连任意地址,把网络暴露面扩到插件自己手里 |
| 资产装载的实际路径 | 本插件不发任何直连请求。URL 资产一律经内核注入的 transport 读取,而宿主侧唯一的 transport 实现是 `assets:read`:只 GET、只 https 与回环 http、不带凭证、上限 512KB、超时 10 秒、三态结果、限流 20 次 / 10 秒,由宿主统一落实(见 7.1) |
| 契约上是两回事 | 「插件自建联网通道」与「插件经由宿主受控通道取字节」是两条不同的契约:前者的暴露面由插件决定,后者的暴露面由宿主决定、插件只能申请。条款约束前者,不否定后者 |
| 机检会不会命中 | 不会。机检扫描只识别全局直接调用(全局 `fetch`、`XMLHttpRequest` 等);经宿主通道的取件不经过这些全局名字,扫描不会把它判成「自行联网」。本插件源码中也不出现全局 `fetch` 调用 |
| 残余的差异 | 条款字面仍是「不自行发起任何网络请求」,严格读会把经宿主通道的取件也包进去;这不是本插件能单方面消除的 |
| 处理建议 | 由 inner 合集侧自行把条款措辞澄清为「不绕开宿主受控通道自行联网」,或等价的表述;本文只记录差异与理由,不代改合集,不改收录条款 |

这一节只回答「两者矛盾吗」:不矛盾,但条款字面与实现口径之间有一个值得合集侧自行澄清的措辞差。市场侧的行为不因条款而改变:取件继续走宿主受控通道,不出现任何直连路径。

- 内核的分类、策略解析、注入拼接与装配:见 [内核与资产](kernel-and-assets.md)。
- 合集如何收录、构建、签名与分发:属各合集仓库,本文只消费其发布布局。
